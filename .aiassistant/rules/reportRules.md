# Report Rules

이 문서는 Sadari 프로젝트의 정책, 성능 개선, 기술 분석, 설계, 배포 및 운영 보고성 Markdown 문서 작성 규칙을 정의합니다.
`docs` 아래의 보고성 Markdown 문서를 생성하거나 수정할 때 아래 규칙을 예외 없이 적용합니다.
규칙은 보안, 사실 정확성, 구현 동기화, 문서 유형별 필수 내용, 형식, 검증과 형상 관리 순으로 중요도가 높은 항목부터 나열합니다.

## 1. 공통 작성 규칙

### 1.1 문체

- 보고 문서는 대화체가 아닌 객관적인 한국어 문어체로 작성합니다.
- 사용자 정책과 운영 절차는 존댓말 서술체를 사용합니다.
- 성능 개선과 기술 분석 및 설계 문서는 `한다`, `했다`, `이다` 형태의 문어체를 사용할 수 있습니다.
- 하나의 문서 안에서는 존댓말 서술체와 `한다` 형태의 문어체를 혼용하지 않습니다.
- 제목과 표의 항목명은 의미가 분명한 명사형으로 작성할 수 있습니다.
- 이모티콘과 이모지를 사용하지 않습니다.
- 감정적인 표현, 과장된 표현, 근거 없는 평가를 사용하지 않습니다.
- 같은 내용을 여러 절에서 반복하지 않고 가장 관련 있는 절에서 한 번만 설명합니다.

### 1.2 기본 구성

- 문서 첫 줄에는 문서의 대상을 명확히 나타내는 1단계 제목을 작성합니다.
- 문서 초반에는 목적, 적용 범위, 기준일 또는 작업일을 확인할 수 있는 개요를 작성합니다.
- 구현 완료 내용과 계획 또는 제안 내용을 같은 문장으로 섞지 않습니다.
- 아직 구현하지 않은 내용은 `예정`, `제안`, `미적용` 중 실제 상태를 명시합니다.
- 독자가 결론과 핵심 변경을 먼저 확인할 수 있도록 중요한 내용을 앞에 배치합니다.
- 항목 비교가 필요한 경우 표를 사용하고, 처리 순서가 중요한 경우 번호 목록을 사용합니다.

## 2. 문서 범위와 저장 위치

### 2.1 적용 대상

- `docs` 아래에 생성하는 정책, 성능 개선, 기술 분석, 설계, 배포, 장애 대응 및 운영 절차 Markdown 문서에 이 규칙을 적용합니다.
- `AGENTS.md`와 `.aiassistant/rules` 아래의 규칙 문서는 프로젝트 관리 문서이므로 이 규칙의 보고서 구성 항목을 강제하지 않습니다.
- 소스 코드 내부 주석과 Javadoc 및 JSDoc에는 각 기술 영역의 규칙을 적용합니다.

### 2.2 저장 위치

- 서비스 정책 문서는 `docs/policies`에 저장합니다.
- 성능 개선 사례는 `docs/performance`에 저장합니다.
- 아키텍처와 기술 설계 문서는 `docs/architecture`에 저장합니다.
- 배포와 장애 대응 및 운영 절차는 `docs/operations`에 저장합니다.
- 기존 문서가 다른 위치에 있으면 요청 범위와 연관된 경우에만 이동하고, 링크와 참조를 함께 수정합니다.

### 2.3 파일명

- 파일명은 영문 소문자 kebab-case와 `.md` 확장자를 사용합니다.
- `report`, `document`, `result`처럼 대상을 알 수 없는 포괄적인 이름을 사용하지 않습니다.
- 문서의 업무 대상과 목적을 파일명에서 확인할 수 있게 작성합니다.

## 3. 보안 및 개인정보

- 비밀번호, Access Token, Refresh Token, API Secret, 개인키, 서비스 계정 JSON 원문을 문서에 기록하지 않습니다.
- 실제 사용자 식별값, 이메일, 전화번호, OAuth 식별값 및 운영 DB 데이터를 문서 예시에 사용하지 않습니다.
- IP, 도메인, 계정명처럼 환경별로 공개하면 안 되는 값은 `<host>`, `<domain>`, `<username>` 형식의 자리표시자로 작성합니다.
- 환경변수와 Secret의 이름은 기록할 수 있지만 실제 값은 기록하지 않습니다.
- 로그와 오류 예시는 민감정보를 제거하고 원인 파악에 필요한 최소 내용만 포함합니다.

## 4. 사실과 근거

### 4.1 현재 구현 확인

- 현재 동작을 설명하기 전에 관련 코드, SQL, 설정, 스키마 또는 실행 결과를 직접 확인합니다.
- 기억이나 추측만으로 구현 상태를 단정하지 않습니다.
- 코드와 DB 및 설정이 서로 다르면 실제 실행 기준과 불일치 내용을 구분하여 기록합니다.
- 날짜에 따라 달라지는 값은 문서의 기준일과 확인 환경을 함께 기록합니다.

### 4.2 측정값과 추정값

- 직접 측정한 값, 소스에서 계산한 값, 예상 효과를 서로 구분합니다.
- 직접 측정하지 않은 응답 시간과 처리량 및 개선율을 실측 결과처럼 작성하지 않습니다.
- 계산으로 구한 수치는 계산식과 비교 기준을 함께 기록합니다.
- 예상 효과는 `예상`, `추정`, `환경에 따라 달라짐`을 명시합니다.
- 실패하거나 확인하지 못한 검증은 생략하지 않고 제한사항으로 기록합니다.

## 5. 정책 문서

- 정책의 대상 사용자와 적용 조건을 먼저 작성합니다.
- 정상 흐름, 예외 흐름, 실패 처리, 복구 또는 취소 가능 여부를 구분합니다.
- 상태값과 공통코드는 코드와 의미를 표로 정리합니다.
- 기간, 횟수, 보존 범위, 공개 여부처럼 데이터에 영향을 주는 기준을 명시합니다.
- 사용자 화면 정책과 서버 검증 정책이 다르면 각각 구분하여 작성합니다.
- 정책상 결정되지 않은 항목을 현재 정책처럼 단정하지 않습니다.
- 문서 마지막에는 관련 구현 파일과 공통코드 및 테이블을 구현 근거로 작성합니다.

## 6. 성능 개선 문서

### 6.1 필수 내용

- 개선 대상 화면, API, 배치 또는 쿼리를 개요에 작성합니다.
- 개선 전 증상과 병목 원인을 구분하여 작성합니다.
- 개선 전후의 호출 구조, SQL 횟수, 처리 범위 또는 알고리즘 차이를 설명합니다.
- 선택한 개선 방식과 함께 복잡도, 메모리, 데이터 정합성 및 유지보수 측면의 trade-off를 작성합니다.
- 검증 방법과 아직 측정하지 못한 항목을 작성합니다.
- 관련 소스 파일과 Mapper 및 SQL 식별자를 구현 근거로 작성합니다.

### 6.2 성능 수치

- 응답 시간, 처리량, CPU, 메모리, 논리 읽기 등의 수치는 측정 환경과 데이터 건수 및 반복 횟수를 함께 기록합니다.
- 평균값만 사용하지 않고 필요하면 중앙값, 상위 95% 응답 시간 또는 최댓값을 함께 기록합니다.
- SQL 호출 수처럼 소스에서 확인한 값은 `호출 횟수 감소`로 표현하고 실제 응답 시간 개선율과 구분합니다.
- 실행 계획을 비교한 경우 주요 접근 경로, 예상 비용, 인덱스 사용 여부를 함께 기록합니다.
- 비교 조건이 다른 측정 결과를 같은 기준의 개선 결과처럼 작성하지 않습니다.

## 7. 분석 및 설계 문서

- 현재 구조와 문제를 `현행`으로 작성하고 목표 구조를 `개선안`으로 구분합니다.
- 요구사항, 전제조건, 제외 범위를 먼저 확정합니다.
- 선택한 설계와 대안을 함께 기록하고 선택 이유와 trade-off를 설명합니다.
- 데이터 흐름, 트랜잭션 경계, 실패 처리, 동시성 및 보안 영향을 검토합니다.
- DB 설계는 테이블과 컬럼의 역할, 키 전략, Null 정책, 이력 및 삭제 정책을 포함합니다.
- 구현 전 설계 문서에는 DB와 소스에 아직 적용하지 않았음을 명시합니다.

## 8. 배포 및 운영 문서

- 사전 조건, 설정 항목, 실행 순서, 검증 방법, 실패 시 복구 순서로 작성합니다.
- 환경변수는 Secret과 일반 Variable을 구분합니다.
- 명령 예시는 실행 위치와 필요한 권한을 확인할 수 있게 작성합니다.
- 배포 성공 판단 기준과 health check 경로를 명시합니다.
- 롤백 절차와 데이터 마이그레이션 실패 시 중단 기준을 작성합니다.
- 특정 개발자 PC에서만 유효한 절대 경로를 운영 절차에 사용하지 않습니다.

## 9. 구현 근거와 참조

- 소스 파일은 저장소 루트 기준 상대 경로로 작성합니다.
- 클래스명, 메서드명, Mapper SQL ID, 테이블명 및 공통코드는 백틱으로 표시합니다.
- 자주 변경되는 줄 번호에만 의존하지 않고 파일 경로와 심볼명을 함께 작성합니다.
- 긴 소스 전체를 복사하지 않고 설명에 필요한 최소 코드만 인용합니다.
- 외부 문서를 참조하면 공식 문서 또는 원본 저장소를 우선하고 문서 제목과 링크를 함께 작성합니다.
- 존재하지 않는 파일, API, 테이블 및 공통코드를 구현 근거에 작성하지 않습니다.

## 10. 구현 변경과 문서 동기화

- 문서화된 정책, 성능 구조, 배포 절차 또는 데이터 구조를 변경하면 같은 작업에서 관련 문서도 수정합니다.
- 구현에서 제거된 화면, 상태, 메시지, API 및 SQL을 문서에 현재 기능으로 남기지 않습니다.
- 문서만 먼저 작성한 경우 구현 완료 여부를 명시하고 구현된 것처럼 표현하지 않습니다.
- 여러 문서가 같은 정책을 설명하면 기준 문서를 정하고 다른 문서에서는 중복 설명 대신 링크를 사용합니다.
- 새 문서나 문서 범주를 추가하면 해당 디렉토리의 `README.md` 또는 문서 인덱스에 연결합니다.
- 문서 이동이나 파일명 변경 시 저장소 내부의 기존 링크를 함께 수정합니다.

## 11. Markdown 형식

- 파일은 UTF-8로 저장하고 한글이 깨지지 않는지 확인합니다.
- 제목 단계는 한 단계씩 증가시키며 1단계 제목은 문서당 하나만 사용합니다.
- 코드, 파일 경로, API 경로, 테이블명, 컬럼명, 공통코드 및 환경변수는 백틱으로 표시합니다.
- 표의 열은 같은 종류의 정보를 담고 숫자 열은 오른쪽 정렬을 사용합니다.
- 코드 블록에는 가능한 경우 `java`, `sql`, `typescript`, `yaml`, `bash`와 같은 언어를 지정합니다.
- 문서 안에 원시 HTML을 사용하지 않고 Markdown 표현을 우선합니다.
- 불필요한 후행 공백과 연속된 빈 줄을 남기지 않습니다.

## 12. 품질 검증

- 문서에 작성한 파일, 메서드, SQL ID, API, 테이블 및 공통코드가 실제로 존재하는지 확인합니다.
- 정책과 구현이 일치하는지 관련 기술 규칙과 함께 대조합니다.
- 내부 링크와 상대 경로가 유효한지 확인합니다.
- 한글 인코딩과 표 및 코드 블록 렌더링을 확인합니다.
- 변경 문서에 `git diff --check`를 실행하여 공백 오류를 확인합니다.
- 성능 문서는 측정값과 계산값 및 예상값이 명확히 구분되는지 다시 확인합니다.
- 검증하지 못한 항목과 잔여 위험은 최종 결과에 보고합니다.

## 13. Git 규칙

- 보고성 문서만 변경하는 커밋은 `docs:` 접두사를 사용합니다.
- 구현 변경과 문서 동기화가 함께 있으면 구현의 주된 목적에 맞는 커밋 접두사를 사용합니다.
- 임시 측정 로그, 운영 데이터 덤프, 실행 계획 원본 및 민감정보 파일을 커밋하지 않습니다.
