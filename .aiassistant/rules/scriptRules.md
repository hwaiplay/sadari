# Script Rules

이 문서는 Sadari 프로젝트의 React, TypeScript, JavaScript, 화면 메시지, API 호출 및 배포 스크립트 규칙을 정의합니다.
프론트엔드와 배포 스크립트를 생성하거나 수정할 때 아래 규칙을 예외 없이 적용합니다.
규칙은 보안과 실행 안정성, 상태 무결성, 타입과 형식, 문서화, 화면 품질, 검증과 형상 관리 순으로 나열합니다.

## 1. 공통 주석 작성 규칙

### 1.1 문체

- JavaScript, TypeScript, JSX 및 셸 스크립트 주석은 모두 `한다`, `이다`, `된다` 형태의 반말 서술체로 작성합니다.
- 주석에 `합니다`, `입니다`, `됩니다` 형태의 존댓말을 사용하지 않습니다.
- 주석에 이모티콘과 이모지를 사용하지 않습니다.
- 주석에 느낌표와 물음표를 사용하지 않습니다.

### 1.2 내용

- 사용자에게 노출되는 실제 문구를 인용한 주석은 접두사 없이 원문만 작성하며 문구 안의 문체와 문장부호는 예외로 둡니다.
- 코드 내용을 그대로 읽는 주석은 작성하지 않고 구현 이유, 화면 정책 및 실패 시 처리 방향을 설명합니다.
- 어느 함수나 변수에도 적용할 수 있는 포괄적인 설명을 사용하지 않고 실제 업무 대상과 목적을 작성합니다.

## 2. 설정 보안 및 로그

### 2.1 환경별 설정

- API URL, 포트, 비밀값, 토큰 만료 시간 등 환경별 설정을 코드에 하드코딩하지 않습니다.
- 브라우저에 공개해도 되는 값만 `VITE_` 환경변수로 관리합니다.
- 비밀번호, 개인키, 서비스 계정 JSON 및 서버 전용 비밀값을 프론트엔드 환경변수에 넣지 않습니다.
- 반복되는 도메인 코드는 공통 상수 또는 공통코드 API 응답으로 관리합니다.

### 2.2 로그 보안

- 로그에 Access Token, Refresh Token, 비밀번호, 개인키, 서비스 계정 JSON 및 개인정보를 출력하지 않습니다.
- 운영 코드에 임시 `console.log`를 남기지 않습니다.
- 오류 로그에는 원인 파악에 필요한 최소 문맥만 기록하며 서버 응답의 원시 스택 트레이스를 출력하지 않습니다.

### 2.3 로그 호출 형식

- 로그 치환값 또는 추가 출력값이 2개 이하이면 로그 호출 전체를 한 줄에 작성합니다.
- 출력값이 3개 이상이면 메시지 다음 줄부터 값을 작성하고 같은 들여쓰기 위치에 정렬합니다.
- 로그 호출 형식 때문에 민감정보 비출력 규칙을 위반하지 않습니다.

## 3. API 호출 및 응답 검증

### 3.1 공통 응답

- 모든 API 응답은 공통 `ResultData` 구조를 검증합니다.
- HTTP 2xx만으로 성공 처리하지 않고 `ResultData.code === 200`인지 확인합니다.
- 실패 코드이면 서버의 `message`를 공통 알림으로 사용자에게 보여줍니다.
- 반복되는 성공 및 실패 판정은 프로젝트 공통 응답 유틸리티를 사용합니다.

```json
{
  "code": 200,
  "message": "처리가 완료되었습니다.",
  "data": {}
}
```

### 3.2 오류 노출

- 원시 Axios 오류, 서버 스택 트레이스 및 내부 예외 메시지를 화면에 직접 노출하지 않습니다.
- API 응답에 사용자 메시지가 없으면 프로젝트 공통 오류 문구를 사용합니다.
- 인증 만료와 일반 업무 실패를 구분하여 로그인 이동과 현재 화면 오류 처리를 분리합니다.

### 3.3 API 계약

- 요청 필드명, 응답 필드명, 코드값 및 경로는 백엔드 API 계약과 동일하게 유지합니다.
- 백엔드 API 계약이 변경되면 관련 타입, API 모듈, Query Key 및 화면 사용처를 같은 변경에서 수정합니다.

### 3.4 CSRF Token 전송

- Cookie 인증 API의 `POST`, `PUT`, `PATCH`, `DELETE` 요청은 공통 API Client가 CSRF Token을 조회하고 요청 Header에 자동으로 설정합니다.
- 화면별 API 모듈에서 CSRF Header를 반복 구현하지 않고 공통 Axios Request Interceptor를 사용합니다.
- Service Worker처럼 Axios를 사용할 수 없는 실행 환경은 같은 CSRF Token 조회 API와 Header 규칙을 공통 함수로 구현합니다.
- CSRF Token 불일치로 `403`이 발생하면 Token을 한 번만 다시 조회하고 원 요청을 한 번만 재시도하여 무한 반복을 방지합니다.
- 인증 갱신과 로그아웃 요청도 상태 변경 요청이므로 CSRF 검증에서 제외하지 않습니다.

## 4. 입력 검증 및 실패 처리

### 4.1 입력값 검증

- API 요청값, 라우트 파라미터, 외부 API 응답 및 선택된 상태값을 참조하기 전에 비어 있는지 검증합니다.
- 등록 및 수정 함수는 진입 직후 필수 입력값을 검증합니다.
- 코드값과 정렬 조건처럼 허용 범위가 정해진 값은 허용 목록 또는 공통코드 목록으로 검증합니다.
- 문자열, 배열 및 객체에 맞는 타입 안전한 검증 방법을 사용합니다.
- 모바일 PWA의 프로필 및 배경 이미지 선택은 브라우저에서 고해상도 원본을 디코딩하지 않고 사용자 전용 비공개 서버 임시 저장소에 업로드한 뒤, 서버가 방향 보정과 축소를 완료한 미리보기만 화면 상태에 반영합니다.
- 서버 임시 이미지 식별값은 로그인 사용자와 이미지 유형에 종속시키고, 재선택·편집 취소·최종 저장·로그아웃·계정 비활성화·영구 탈퇴 시 삭제하며 30분이 지나면 만료 처리합니다.
- 앱이 다시 시작되어도 같은 로그인 사용자의 만료되지 않은 임시 선택본은 복원하되 공개 URL, 알림 및 소셜 화면에는 노출하지 않습니다.

### 4.2 실패 처리

- API 호출과 외부 연동은 실패 경로를 포함하여 작성합니다.
- 비동기 API 호출의 예외를 `try-catch` 또는 React Query의 공통 오류 경로로 격리합니다.
- 사용자에게 처리 성공을 알리기 전에 공통 응답 코드와 필요한 데이터가 모두 유효한지 확인합니다.

## 5. 비동기 처리

### 5.1 요청 상태

- 요청 시작, 성공, 실패 및 완료 상태를 명확히 관리합니다.
- 등록, 수정 및 삭제 요청의 중복 제출을 방지합니다.
- 같은 조회 요청이 동시에 중복 실행되지 않도록 Query Key와 진행 상태를 재사용합니다.

### 5.2 정리 및 재시도

- 컴포넌트가 해제된 뒤 불필요한 상태 변경이 발생하지 않도록 React Query 또는 정리 함수를 사용합니다.
- API 실패 후 무한 재시도나 로그인 리다이렉트 반복이 발생하지 않도록 재시도 조건을 제한합니다.
- 타이머, 이벤트 리스너, Observer 및 구독은 Effect 정리 함수에서 해제합니다.

### 5.3 상태 변경 작업 중 화면 이탈 차단

- 등록, 수정, 삭제, 파일 업로드 및 외부 설정 변경처럼 서버나 외부 서비스의 상태를 변경하는 모든 사용자 작업에는 공통 처리 중 모달과 화면 이동 가드를 적용합니다.
- 처리 중 모달은 요청 시작부터 최종 성공 또는 실패 응답이 확정될 때까지 유지하며 확인 버튼과 취소 버튼을 모두 표시하지 않습니다.
- 처리 중 모달은 바깥 영역 클릭, Escape 키 및 배경 화면 조작으로 닫히지 않게 합니다.
- PWA 스와이프, 브라우저 뒤로가기 및 하드웨어 뒤로가기는 동일 URL의 History 가드로 실제 화면 이탈을 차단합니다.
- 새로고침과 창 닫기는 브라우저가 제공하는 `beforeunload` 보호 범위 안에서 차단하며 운영체제 제스처 자체를 비활성화할 수 있다고 가정하지 않습니다.
- 상태 변경 API는 공통 Axios Interceptor에서 이동 차단을 적용하여 개별 화면의 누락을 방지합니다.
- 인증 갱신과 로그아웃 및 저장 없이 계산 결과만 조회하는 POST 요청은 상태 변경 작업에서 명시적으로 제외합니다.
- 파일 변환, 브라우저 권한 요청 및 외부 SDK Token 발급처럼 상태 변경 API 전에 필요한 비동기 단계가 있으면 공통 작업 실행 함수로 전체 단계를 감쌉니다.
- 여러 상태 변경 요청이 중첩되면 모든 요청이 완료될 때까지 하나의 처리 중 모달과 이동 가드를 유지합니다.
- 최종 응답 이후 성공 및 실패 알림이나 라우팅을 실행하기 전에 처리 중 모달과 History 가드를 먼저 해제합니다.
- 클라이언트 요청 취소가 서버의 저장 취소를 보장하지 못하므로 처리 중 모달에 취소 기능을 제공하지 않습니다.

### 5.4 조회 로딩 상태

- 모달 내부에서 데이터를 조회하는 동안에는 요청의 시작, 성공, 실패 및 완료 상태와 연결한 공통 소형 회전 링을 표시합니다.
- 모달 조회 로딩은 공통 `Loading` 컴포넌트의 소형 모드를 재사용하고 화면에 `목록 조회 중` 같은 별도 텍스트를 표시하지 않습니다.
- 화면에서 로딩 문구를 숨기더라도 `role="status"`와 `aria-label`로 조회 진행 상태를 보조기기에 전달합니다.
- 페이지 최초 조회 로딩 문구는 현재 pathname으로 사용자 메뉴 API를 호출하여 `TM_URMENU`에 등록된 현재 메뉴명을 조회한 뒤 `{메뉴명} 조회 중...` 형식으로 구성합니다.
- 현재 경로에 등록된 메뉴명이 없거나 사용자 메뉴 조회에 실패하면 페이지 최초 조회 로딩 문구로 `목록 조회 중...`을 사용합니다.
- 페이지 로딩과 헤더는 같은 사용자 메뉴 Query Key와 캐시를 공유하여 현재 메뉴 조회 API를 중복 호출하지 않습니다.
- 로그인, 등록, 수정 및 삭제처럼 작업 대상이 별도로 정해진 처리 중 문구는 메뉴명 기반 페이지 조회 문구로 변경하지 않습니다.

## 6. React 상태 및 Hooks

### 6.1 상태 무결성

- State 객체와 배열을 직접 변경하지 않습니다.
- 스프레드 연산자, `map`, `filter` 등으로 새로운 객체와 배열을 만들어 갱신합니다.
- 서버 상태는 프로젝트의 React Query 패턴을 따릅니다.
- 같은 서버 데이터를 여러 컴포넌트에서 중복 요청하지 않고 공통 Query Key와 캐시를 재사용합니다.

### 6.2 Hooks

- `useEffect`, `useCallback`, `useMemo`가 참조하는 상태와 함수를 의존성 배열에 모두 포함합니다.
- `react-hooks/exhaustive-deps` 경고를 비활성화하지 않습니다.
- 렌더링 중 상태를 변경하지 않습니다.
- 계산 가능한 값은 별도 State와 Effect로 중복 관리하지 않고 렌더링 또는 `useMemo`에서 계산합니다.
- Hook은 조건문, 반복문 및 중첩 함수 안에서 호출하지 않습니다.

### 6.3 모바일 PWA 홈 종료 안내

- 모바일 PWA 홈 종료 안내는 지원 브라우저에서 `CloseWatcher`를 우선 사용하고 미지원 브라우저에서만 동일 URL History 가드를 사용합니다.
- `CloseWatcher`와 History 종료 가드를 동시에 설치하지 않아 한 번의 기기 뒤로가기가 두 감지 수단에 중복 소비되지 않게 합니다.
- 첫 번째 시스템 뒤로가기에서 홈 종료 안내를 표시한 뒤에는 감지 수단을 즉시 복원하지 않고 다음 요청을 운영체제 종료 동작으로 전달합니다.
- 사용자가 종료 안내의 취소 버튼을 눌렀을 때만 브라우저에 맞는 종료 감지 수단을 복원해 다음 첫 번째 뒤로가기를 다시 감지합니다.

## 7. TypeScript 타입 안정성

### 7.1 기본 타입 규칙

- `const`를 기본으로 사용하고 재할당이 필요한 경우에만 `let`을 사용합니다.
- 동등 비교에는 `===`와 `!==`를 사용합니다.
- `any`로 타입 오류를 숨기지 않고 실제 요청, 응답 및 화면 상태 구조를 타입으로 정의합니다.
- TypeScript 오류를 불필요한 타입 단언이나 이중 단언으로 우회하지 않습니다.
- Null 가능성이 있는 값은 타입과 분기에서 명시적으로 처리합니다.

### 7.2 정적 분석

- ESLint 및 TypeScript 오류와 경고를 모두 해결합니다.
- 외부 모듈은 현재 TypeScript 설정에서 실제로 제공하는 export 형식에 맞춰 import합니다.
- `allowSyntheticDefaultImports`에 의존하는 기본 import를 사용하지 않고 named export 또는 namespace export를 사용합니다.
- 타입으로만 사용하는 모듈 항목은 `import type`으로 선언합니다.
- 사용하지 않는 import, 변수, 타입 및 함수는 즉시 삭제합니다.
- Raw 객체 대신 구체적인 인터페이스, 타입 별칭 또는 제네릭을 사용합니다.
- 경고 억제 주석으로 문제를 숨기지 않고 원인을 수정합니다.

## 8. 함수 파라미터 및 객체 생성

### 8.1 함수 파라미터

- 함수 파라미터가 3개 이하이면 한 줄에 작성합니다.
- 함수 파라미터가 4개 이상이면 한 줄에 최대 3개까지 작성하고 다음 파라미터부터 줄바꿈합니다.
- 줄바꿈한 파라미터는 첫 번째 파라미터의 시작 위치를 기준으로 세로 정렬합니다.
- 파라미터가 계속 늘어나면 개별 파라미터 대신 의미 있는 요청 객체로 묶을 수 있는지 먼저 검토합니다.

### 8.2 객체 생성

- `new`를 사용하는 객체 변수 선언과 생성자 호출은 줄바꿈하지 않고 한 줄에 작성합니다.
- 객체 생성 목적을 설명하는 주석은 객체 선언 바로 위에 작성합니다.
- 생성자 파라미터가 많더라도 객체 생성문 자체는 한 줄로 유지합니다.
- 일반 객체 리터럴과 배열 리터럴은 가독성을 위해 여러 줄로 작성할 수 있으며 이 규칙의 대상에서 제외합니다.

```typescript
// 현재 날짜를 기준으로 독서기간을 계산할 날짜 객체를 생성한다
const today = new Date();
```

## 9. 로직 주석 및 코드 형식

### 9.1 함수 시작 공백

- 함수 여는 중괄호 바로 다음에는 빈 줄을 한 줄 작성한 뒤 첫 실행문을 작성합니다.
- 함수 시작 직후 한 줄 주석 또는 여러 줄 주석이 있으면 해당 주석을 빈 줄 한 줄과 동일하게 취급합니다.
- 함수 시작 직후 주석이 있으면 여는 중괄호와 주석 사이에 별도 빈 줄을 작성하지 않습니다.
- React 컴포넌트, Custom Hook, 이벤트 핸들러, 콜백 및 유틸리티 함수에 동일하게 적용합니다.

### 9.2 반환문

- 모든 `return` 바로 위에는 반환값 또는 조기 종료 목적을 구체적으로 설명하는 한글 주석을 작성합니다.
- 반환 주석과 `return` 사이에는 빈 줄을 작성하지 않습니다.
- JSX를 반환할 때는 어떤 화면 또는 컴포넌트 구조를 반환하는지 작성합니다.
- `반환 결과를 반환한다`처럼 어느 반환문에도 적용할 수 있는 설명을 사용하지 않습니다.

### 9.3 분기와 실행 블록

- `if`, `else if`, `else`, `switch`, `case`, 삼항 연산자 등 모든 분기 바로 위에 분기 이유와 화면 정책을 설명하는 한글 주석을 작성합니다.
- `for`, `forEach`, `map`, `filter`, `reduce`, `while`, `try`, `catch`, `finally`, 콜백 및 지역 블록 바로 위에 목적을 설명하는 한글 주석을 작성합니다.
- 분기와 블록이 단순하더라도 주석을 생략하지 않습니다.
- 블록의 닫는 중괄호 다음 줄은 함수 자체가 끝나는 지점을 제외하고 한 줄 비웁니다.
- 블록 뒤에 `else`, `catch`, `finally`가 이어져도 닫는 중괄호와 다음 키워드 사이를 한 줄 비웁니다.

### 9.4 if 조건절

- `if` 조건절의 여는 괄호와 닫는 괄호 사이에는 한 줄 주석과 여러 줄 주석을 작성하지 않습니다.
- 조건별 설명은 `if` 바로 위의 분기 주석에 판단 기준과 함께 작성합니다.
- 첫 번째 조건은 `if (`와 같은 줄에 작성합니다.
- 여러 줄 조건은 현재 `if` 문의 들여쓰기보다 8칸 더 들여씁니다.
- 한 줄에는 조건을 최대 두 개까지 작성하며 `||` 또는 `&&`를 한 번 사용해 두 조건을 계산한 뒤 줄바꿈합니다.
- 조건 개수가 홀수이면 마지막 줄에는 하나의 조건만 작성할 수 있습니다.
- 이어지는 조건 줄은 이전 줄과 연결되는 `||` 또는 `&&`로 시작하며 같은 세로 위치에 정렬합니다.

```typescript
// 사용자와 응답 정보가 모두 있어야 후속 화면 상태를 갱신한다
if (userNumb !== undefined && resultData.code === 200
        && resultData.data !== undefined) {
  // 검증된 사용자 정보를 화면 상태에 반영한다
  setUser(resultData.data);
}
```

- 여러 호출이 같은 목적을 가지더라도 각 호출 바로 위에 주석을 개별 작성합니다.

## 10. 함수 JSDoc

### 10.1 적용 대상

- 함수 선언문, 함수 표현식, 화살표 함수, React 컴포넌트, Custom Hook, 이벤트 핸들러 및 유틸리티 함수를 포함한 모든 함수 바로 위에 JSDoc을 작성합니다.
- 인라인 콜백처럼 JSDoc을 정상적으로 연결할 수 없는 함수는 별도의 이름 있는 함수로 분리한 뒤 JSDoc을 작성합니다.

### 10.2 작성 형식

- JSDoc은 `/**`로 시작하고 `*/`로 끝내며 각 내부 줄은 `*`로 시작합니다.
- 첫 문장에는 함수의 실제 업무 대상과 처리 목적을 구체적으로 작성합니다.
- 모든 함수에 `@author SeungHyeon.Kang`을 작성합니다.
- 파라미터가 있으면 모든 파라미터에 `@param`과 설명을 작성합니다.
- 반환 여부와 관계없이 모든 함수에 `@return`과 반환값의 의미를 작성합니다.
- 예외가 발생하거나 Promise가 reject될 수 있으면 `@throws`와 발생 조건을 작성합니다.
- JSDoc도 공통 주석의 문체와 문장부호 규칙을 따릅니다.

```typescript
/**
 * 독후감 번호를 사용하여 독후감 상세 화면으로 이동한다
 *
 * @author SeungHyeon.Kang
 * @param reptNumb 이동할 독후감 번호
 * @return 반환값이 없다
 */
const moveReportDetail = (reptNumb: number): void => {
  // 독후감 번호를 경로에 포함하여 상세 화면으로 이동한다
  navigate(`/book/detail/${reptNumb}`);
};
```

## 11. 화면 메시지 주석

### 11.1 사용자 메시지

- JSX 텍스트 노드와 TypeScript 및 JavaScript 문자열 중 사용자 화면이나 보조기기에 노출될 수 있는 문구는 코드에 직접 작성하지 않고 `message` 함수와 메시지 프로퍼티 키로 관리합니다.
- 제목, 페이지 설명, 본문, 라벨, 버튼명, 링크명, 입력 `placeholder`, 도움말, 빈 상태, 로딩 상태, 상태명, 정렬 및 필터 옵션, 단위, 확인 및 오류 문구, 기본값과 대체 문구를 모두 사용자 메시지로 간주합니다.
- `aria-label`, `aria-description`, `title` 및 의미가 있는 이미지 `alt`처럼 화면에 보이지 않더라도 보조기기나 브라우저 UI에 전달되는 문구도 메시지 프로퍼티로 관리합니다.
- 배열, 객체, 상수, 조건식, 템플릿 문자열 및 문자열 결합으로 구성한 표시 문구도 하드코딩 예외로 두지 않습니다.
- 서버가 완성된 표시 문구로 제공한 응답, 사용자가 작성한 콘텐츠, 업무 식별을 위한 내부 코드값, 로그 및 화면에 도달하지 않는 내부 예외 문구는 메시지 프로퍼티 적용 대상에서 제외합니다.
- 내부 기본값이나 예외 문구가 오류 처리 또는 대체 표시 경로를 통해 화면에 노출될 가능성이 있으면 내부 문자열로 간주하지 않고 메시지 프로퍼티로 관리합니다.
- `alert`, toast, SweetAlert, 에러 모달 등 사용자 메시지를 노출하는 코드 바로 위에 실제 화면 문구를 주석으로 작성합니다.
- 메시지 프로퍼티 키를 사용하더라도 해당 키의 기본 언어 원문을 주석에 동일하게 기록합니다.
- 실제 문구 주석 앞에 `화면표시`, `메시지` 같은 접두사를 붙이지 않습니다.

```typescript
// "아이디와 비밀번호를 모두 입력해 주세요."
await sweetWarning(message("frontend.login.required"));
```

### 11.2 JSX 메시지

- JSX에서 `message` 함수로 표시하는 제목, 라벨, 버튼명 및 상태 문구 바로 위에는 JSX 주석으로 실제 기본 언어 문구를 작성합니다.
- 조건식에서 여러 메시지 중 하나를 표시하면 각 분기의 실제 문구를 구분하여 작성합니다.

```tsx
<h2 className={styles.sectionTitle}>
  {/* "공개 여부" */}
  {message("frontend.common.visibility")}
</h2>
```

### 11.3 공통 메시지 키

- 둘 이상의 화면이나 기능에서 의미와 기본 문구가 같은 메시지는 `frontend.common.*` 키를 우선 사용합니다.
- 공통 키를 추가하거나 기존 키로 통합하기 전에 기본 언어와 지원 언어의 문구 및 치환 파라미터가 모두 호환되는지 확인합니다.
- 번역 결과만 우연히 같거나 화면 맥락, 동작, 상태의 의미가 다른 메시지는 기능별 키를 유지합니다.
- 기능별 키를 공통 키로 교체한 뒤에는 정적 참조와 동적 키 조합을 모두 검색하고, 참조가 남지 않은 중복 키를 모든 언어 메시지 파일에서 함께 제거합니다.
- 메시지 키를 추가, 변경 또는 삭제할 때는 기본 언어와 영어를 포함한 모든 지원 언어 메시지 파일을 같은 작업에서 함께 수정합니다.
- 모든 지원 언어 메시지 파일은 키 집합이 정확히 일치해야 하며 동일 파일 안에 중복 키를 작성하지 않습니다.
- 치환 파라미터가 있는 메시지는 모든 지원 언어에서 파라미터의 이름, 개수 및 의미를 동일하게 유지합니다.

## 12. 화면 영역 접근성 및 DOM

### 12.1 화면 영역 주석

- 키보드 포커스와 Enter 및 Space 조작을 고려합니다.
- 동적 목록에는 배열 순서가 아닌 안정적인 `key`를 사용합니다.

### 14.1 파일명

- 외부 라이브러리 계약으로 이름이 고정된 구현 메서드만 예외로 하며 타입 선언으로 계약 근거를 확인할 수 있어야 합니다.
- 조회 함수는 `get`, 등록 함수는 `set`, 수정 함수는 `upt`, 삭제 함수는 `del`, 중복 검사는 `dup` 접두사를 우선 사용합니다.
- 이벤트 핸들러는 기존 프로젝트의 `handle***` 또는 `on***` 규칙을 일관되게 사용합니다.
- boolean 값과 판정 함수는 `is`, `has`, `can`, `should` 중 의미에 맞는 접두사를 사용합니다.

## 15. 배포 및 셸 스크립트

### 15.1 보안

- 비밀값과 환경별 URL을 스크립트에 하드코딩하지 않습니다.
- 환경변수 또는 GitHub Secrets를 사용합니다.
- 로그에 토큰, 비밀번호, 개인키 및 서비스 계정 JSON을 출력하지 않습니다.

### 15.2 실행 안정성

- 실패를 무시하지 않도록 명령의 종료 코드를 검사합니다.
- Bash 배포 스크립트는 가능한 경우 `set -euo pipefail`을 사용합니다.
- 파일 삭제, 이동 및 배포 대상 경로는 실행 전에 예상된 작업 디렉토리인지 확인합니다.
- 배포 단계가 실패하면 다음 단계를 계속 실행하지 않습니다.

## 16. 품질 검증

### 16.1 필수 검사

- 수정 후 `npm run lint`를 실행합니다.
- 수정 후 `npx tsc --noEmit`을 실행하여 IDE에서 표시되는 TypeScript 오류까지 확인합니다.
- 사용자 화면이나 빌드 결과에 영향을 주는 변경은 `npm run build`로 검증합니다.
- 프론트엔드 코드나 메시지 프로퍼티를 수정한 뒤에는 `.ts`, `.tsx`, `.js`, `.jsx` 전체를 대상으로 사용자 노출 문자열 하드코딩 여부를 정적 검사하고 발견된 문구를 메시지 프로퍼티로 전환합니다.
- 하드코딩 검사는 한글 문자열만 검색하지 않고 영문 문구, 단위, 기본값, 대체 문구, 접근성 속성, 배열 및 객체의 표시값, 템플릿 문자열과 문자열 결합까지 포함합니다.
- 정적으로 작성한 모든 `message("...")` 호출의 키가 기본 언어와 모든 지원 언어 파일에 존재하는지 검사합니다.
- 모든 지원 언어 메시지 파일의 키 집합, 중복 키 및 치환 파라미터 일치 여부를 검사합니다.
- 정적 검사에서 제외한 문자열은 화면에 도달하지 않는 내부 코드, 로그, 내부 예외 또는 서버 제공 표시값인지 사용 경로를 확인하며 파일이나 디렉토리 단위의 포괄적 제외 목록을 두지 않습니다.
- IDE의 오류와 경고를 남기지 않습니다.
- 경고 비활성화 주석으로 문제를 숨기지 않습니다.

### 16.2 화면 검증

- 화면 변경은 모바일과 데스크톱 너비에서 텍스트 잘림, 겹침 및 가로 스크롤을 확인합니다.
- 모달, 드롭다운, 달력 및 고정 네비게이션의 쌓임 순서와 스크롤 위치를 확인합니다.
- 로딩, 빈 목록, 오류, 비활성화 및 권한 거부 상태를 함께 확인합니다.

## 17. Git 규칙

커밋 메시지는 다음 접두사 중 하나로 시작합니다.

- `feat:` 기능 추가
- `fix:` 버그 수정
- `refactor:` 동작 변경 없는 구조 개선
- `docs:` 문서 수정
- `style:` 동작 변경 없는 포맷 수정

예: `fix: 독후감 저장 실패 응답 처리`
