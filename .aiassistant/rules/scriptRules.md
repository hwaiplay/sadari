# Script Rules

이 문서는 Sadari 프로젝트의 React, TypeScript, JavaScript, 화면 메시지, API 호출 및 린트 규칙을 정의합니다.
프론트엔드와 배포 스크립트를 생성하거나 수정할 때 아래 규칙을 예외 없이 적용합니다.
규칙은 주석 공통 정책, 비밀정보 보호, API 안정성, 상태 무결성, 타입과 접근성, 문서화와 명명, 품질 검증, 형상 관리 순으로 중요도가 높은 항목부터 나열합니다.

## 1. 공통 주석 작성 규칙

- JavaScript, TypeScript, JSX 및 셸 스크립트 주석은 모두 `한다`, `이다`, `된다` 형태의 반말 서술체로 작성합니다.
- 주석에 `합니다`, `입니다`, `됩니다` 형태의 존댓말을 사용하지 않습니다.
- 주석에 이모티콘과 이모지를 사용하지 않습니다.
- 주석에 느낌표와 물음표를 사용하지 않습니다.
- 사용자에게 노출되는 실제 문구를 인용한 주석은 접두사 없이 원문만 작성하며 문구 안의 문체와 문장부호는 예외로 둡니다.
- 코드 내용을 그대로 읽는 주석은 작성하지 않고 구현 이유와 화면 정책을 설명합니다.

## 2. 배포 및 셸 스크립트 보안

- 비밀값과 환경별 URL을 스크립트에 하드코딩하지 않습니다.
- 환경변수 또는 GitHub Secrets를 사용합니다.
- 실패를 무시하지 않도록 셸 스크립트에서 종료 코드를 검사합니다.
- Bash 배포 스크립트는 가능한 경우 `set -euo pipefail`을 사용합니다.
- 로그에 토큰, 비밀번호, 개인키 및 서비스 계정 JSON을 출력하지 않습니다.

## 3. API 호출 및 응답 검증

- 모든 API 응답은 공통 `ResultData` 구조를 검증합니다.
- HTTP 2xx만으로 성공 처리하지 않고 `ResultData.code === 200`인지 확인합니다.
- 실패 코드이면 서버의 `message`를 공통 알림으로 사용자에게 보여줍니다.
- 비동기 API 호출의 예외를 `try-catch` 또는 React Query의 공통 에러 경로로 격리합니다.
- 원시 Axios 오류나 서버 스택 트레이스를 화면에 직접 노출하지 않습니다.
- 반복되는 성공 및 실패 판정은 프로젝트 공통 응답 유틸리티를 사용합니다.

```json
{
  "code": 200,
  "message": "처리가 완료되었습니다.",
  "data": {}
}
```

## 4. 비동기 처리

- 요청 시작, 성공, 실패, 완료 상태를 명확히 관리합니다.
- 중복 제출과 중복 요청을 방지합니다.
- 컴포넌트가 해제된 뒤 불필요한 상태 변경이 발생하지 않도록 React Query 또는 정리 함수를 사용합니다.
- API 실패 후 무한 재시도나 로그인 리다이렉트 반복이 발생하지 않도록 재시도 조건을 제한합니다.

## 5. React 상태 관리

- State 객체와 배열을 직접 변경하지 않습니다.
- 스프레드 연산자, `map`, `filter` 등으로 새로운 객체와 배열을 만들어 갱신합니다.
- 서버 상태는 프로젝트의 React Query 패턴을 따릅니다.
- 같은 서버 데이터를 여러 컴포넌트에서 중복 요청하지 않고 공통 Query Key와 캐시를 재사용합니다.

## 6. React Hooks

- `useEffect`, `useCallback`, `useMemo`가 참조하는 상태와 함수를 의존성 배열에 모두 포함합니다.
- `react-hooks/exhaustive-deps` 경고를 비활성화하지 않습니다.
- 렌더링 중 상태를 변경하지 않습니다.
- 불필요한 Effect를 만들지 않고 계산 가능한 값은 렌더링 또는 `useMemo`에서 계산합니다.

## 7. ESLint 및 TypeScript

- ESLint 오류와 경고를 모두 해결합니다.
- `const`를 기본으로 사용하고 재할당이 필요한 경우에만 `let`을 사용합니다.
- 동등 비교에는 `===`와 `!==`를 사용합니다.
- 사용하지 않는 import, 변수, 타입, 함수는 즉시 삭제합니다.
- `any`로 타입 오류를 숨기지 않고 실제 데이터 구조를 타입으로 정의합니다.
- TypeScript 오류를 타입 단언만으로 우회하지 않습니다.

## 8. UI 접근성 및 DOM

- 버튼 동작에는 `button`을 사용하고 이동에는 링크 역할을 사용합니다.
- 아이콘 버튼에는 `aria-label`을 제공합니다.
- 중첩 버튼 등 유효하지 않은 DOM 구조를 만들지 않습니다.
- 키보드 포커스와 Enter 및 Space 조작을 고려합니다.
- 동적 목록에는 안정적인 key를 사용합니다.

## 9. REST API 경로

- URI에는 영문 소문자만 사용합니다.
- 단어 구분에는 하이픈을 사용하고 언더바 및 camelCase를 사용하지 않습니다.
- URI는 명사형 리소스로 작성하고 동작은 HTTP Method로 구분합니다.
- 프론트에서 새 API 경로를 작성할 때 백엔드 Controller 규칙과 동일한 경로를 사용합니다.

## 10. 분기 및 복잡한 로직 주석

- `if`, `else if`, `else`, `switch`, `case`, 삼항 연산자 등 모든 분기 바로 위에 분기 이유와 화면 정책을 설명하는 한글 주석을 작성합니다.
- `for`, `forEach`, `map`, `filter`, `reduce`, `while`, `try`, `catch`, `finally` 등 새로운 실행 블록 바로 위에 블록의 목적을 설명하는 한글 주석을 작성합니다.
- 함수 본문 안에서 중괄호로 새로운 지역 블록을 시작할 때도 해당 블록 바로 위에 한글 주석을 작성합니다.
- 분기와 블록이 단순하더라도 주석을 생략하지 않습니다.
- 다른 함수, React Hook, API 모듈, 공통 유틸리티 및 외부 라이브러리 함수를 호출하는 코드 바로 위에 호출 목적을 설명하는 한글 주석을 작성합니다.
- 여러 함수 호출이 같은 목적을 가지더라도 각 함수 호출 바로 위에 주석을 개별 작성합니다.
- 정규식, 날짜 계산 및 비동기 처리 전후에는 구현 이유를 작성합니다.
- 외부 API 연동에는 요청 전제조건과 실패 시 처리 정책을 기록합니다.

## 11. 함수 JSDoc 규칙

- 함수 선언문, 함수 표현식, 화살표 함수, React 컴포넌트, Custom Hook, 이벤트 핸들러 및 유틸리티 함수를 포함한 모든 함수 바로 위에 JSDoc을 작성합니다.
- JSDoc은 `/**`로 시작하고 `*/`로 끝내며 각 내부 줄은 `*`로 시작합니다.
- 첫 문장에는 함수의 역할과 처리 목적을 구체적으로 작성합니다.
- 모든 함수에 `@author`를 작성하며 작성자 이름의 성과 이름 사이에는 마침표를 사용합니다.
- 파라미터가 있으면 모든 파라미터에 `@param`과 설명을 작성합니다.
- 반환 여부와 관계없이 모든 함수에 `@return`과 반환값의 의미를 작성합니다.
- 예외가 발생하거나 Promise가 reject될 수 있으면 `@throws`와 발생 조건을 작성합니다.
- 인라인 콜백처럼 JSDoc을 정상적으로 연결할 수 없는 함수는 별도의 이름 있는 함수로 분리한 뒤 JSDoc을 작성합니다.
- JSDoc도 공통 주석 작성 규칙의 반말, 이모지 및 문장부호 금지 규칙을 따릅니다.

```typescript
/**
 * 독후감 번호를 사용하여 독후감 상세 화면으로 이동한다
 *
 * @author SeungHyeon.Kang
 * @param reptNumb 이동할 독후감 번호
 * @return 반환값이 없다
 */
const moveReportDetail = (reptNumb: number): void => {
  // 독후감 번호를 경로에 포함하여 상세 화면으로 이동한다
  navigate(`/book/detail/${reptNumb}`);
};
```

## 12. 화면 메시지 주석

- `alert`, toast, SweetAlert, 에러 모달 등 사용자 메시지를 노출하는 코드 바로 위에 실제 화면 문구를 주석으로 작성합니다.
- 메시지 프로퍼티 키를 사용하더라도 해당 키의 원문을 주석에 동일하게 기록합니다.
- 다국어 문구가 있다면 기본 화면 언어의 문구를 기준으로 기록합니다.

```typescript
// 필수 입력 안내에 사용할 다국어 메시지를 조회한다
const requiredMessage = message("frontend.login.required");

// "아이디와 비밀번호를 모두 입력해 주세요."
await sweetWarning(requiredMessage);
```

## 13. 파일 명명 규칙

- React 화면과 컴포넌트 파일은 PascalCase로 작성합니다.
- 예: `UserDetail.tsx`, `BookSelector.tsx`
- 헬퍼, 포맷터, API 모듈 등 비컴포넌트 파일은 camelCase로 작성합니다.
- 예: `authHelper.ts`, `dateFormatter.ts`
- 스타일 파일은 해당 컴포넌트명과 연결되는 기존 프로젝트 명명 방식을 따릅니다.

## 14. 품질 검증

- 수정 후 `npm run lint`를 실행합니다.
- 사용자 화면이나 빌드 결과에 영향을 주는 변경은 `npm run build`로 검증합니다.
- IDE의 빨간 줄과 경고를 남기지 않습니다.
- 경고 비활성화 주석으로 문제를 숨기지 않습니다.

## 15. Git 규칙

커밋 메시지는 다음 접두사 중 하나로 시작합니다.

- `feat:` 기능 추가
- `fix:` 버그 수정
- `refactor:` 동작 변경 없는 구조 개선
- `docs:` 문서 수정
- `style:` 동작 변경 없는 포맷 수정

예: `fix: 독후감 저장 실패 응답 처리`
