# Core Rules

이 문서는 모든 Sadari 작업에 공통으로 적용하는 최소 필수 규칙을 정의한다. 기술별 상세 형식과 구현 규칙은 `AGENTS.md`의 라우팅 표에 따라 필요한 영역 문서만 추가로 읽는다.

## Rule ID Index

| 규칙 ID | 수준 | 적용 대상 | 검증 방법 |
| --- | --- | --- | --- |
| `CORE-LOAD-001` | MUST | 모든 요청 | 활성 규칙 로드 순서 확인 |
| `CORE-SCOPE-001` | MUST | 모든 요청 | 변경 파일과 활성 규칙 매핑 확인 |
| `CORE-ACTIVE-001` | MUST | 파일 수정 작업 | 수정 전 활성 규칙 ID 안내 확인 |
| `CORE-PRIORITY-001` | MUST | 규칙 충돌 | 우선순위와 예외 사유 확인 |
| `CORE-SECURITY-001` | MUST | 모든 파일과 명령 | 비밀값, 개인정보, 위험 명령 검사 |
| `CORE-INTEGRITY-001` | MUST | 데이터 및 상태 변경 | 검증, 트랜잭션, 실패 경로 확인 |
| `CORE-FUNCTIONAL-001` | MUST | 기능 테스트 | loc 간편 로그인, 테스트 회원 및 실제 화면 검증 확인 |
| `CORE-COMMENT-001` | MUST | 소스 코드 주석 | 문체와 내용 수동 검토 |
| `CORE-CONFIG-001` | MUST | 환경별 설정 | 코드 하드코딩과 설정 동기화 검사 |
| `CORE-ACCOUNT-001` | MUST | 신규 기능과 데이터 범위 확장 | 정책 결정과 문서·코드·테스트 반영 확인 |
| `CORE-MAINT-001` | MUST | 규칙 추가 및 변경 | 중복, 충돌, ID, 검증 방법 확인 |
| `CORE-COMPLETE-001` | MUST | 모든 변경 작업 | 변경 파일별 규칙 재검토와 검증 실행 |
| `CORE-REPORT-001` | MUST | 완료 보고 | 적용 규칙, 검증, 미검증 항목 보고 |

## 1. 규칙 로드와 적용

### CORE-LOAD-001 규칙 로드 순서

- 모든 요청은 다른 분석이나 도구 실행 전에 이 문서를 먼저 읽는다.
- 이 문서를 읽은 뒤 파일명, 확장자, 디렉터리 구조 및 Git 변경 목록으로 작업 영역을 식별한다.
- 상세 소스 내용을 읽거나 수정하거나 실행하기 전에 `AGENTS.md`의 라우팅 표에 해당하는 영역 규칙을 모두 읽는다.
- 요청과 관계없는 영역 규칙은 읽지 않는다.
- 활성 규칙이 작업 도중 변경되면 해당 문서를 다시 읽는다.

### CORE-SCOPE-001 작업 범위 판정

- 변경하거나 상세 분석할 파일별로 적용 영역을 판정한다.
- TSX처럼 로직과 화면 표현이 함께 있는 파일은 관련 영역 규칙을 모두 적용한다.
- 생성될 파일도 확장자와 역할을 기준으로 미리 판정한다.
- 단순 디렉터리 탐색이 상세 파일 조회로 확대되면 확대 전에 필요한 영역 규칙을 읽는다.

### CORE-ACTIVE-001 활성 규칙 안내

- 파일 수정 전에 사용자에게 활성 규칙 문서와 주요 규칙 ID를 짧게 알린다.
- 작업 도중 활성 영역이 늘어나면 추가 규칙을 읽고 추가된 규칙 ID를 알린다.
- 긴 규칙 원문을 반복하지 않고 실제 변경에 직접 영향을 주는 ID를 우선 안내한다.

### CORE-PRIORITY-001 충돌 우선순위

규칙이 충돌하면 다음 순서로 적용한다.

1. 시스템 및 개발자 지침과 사용자의 현재 요청
2. 보안과 개인정보 보호
3. 데이터 무결성과 복구 불가능한 손실 방지
4. 실행 안정성과 실패 격리
5. API 및 데이터 계약
6. 프로젝트 형식과 문서화

- 하위 규칙을 적용하지 못하면 충돌한 규칙 ID와 판단 근거를 최종 결과에 보고한다.
- 코드와 규칙이 다르다는 이유만으로 규칙을 조용히 무시하지 않는다.
- 규칙 자체가 현재 구조와 충돌하면 구현을 임의로 왜곡하지 않고 규칙을 수정하거나 사용자에게 결정을 요청한다.

## 2. 공통 안전과 품질

### CORE-SECURITY-001 보안과 개인정보

- 비밀번호, Access Token, Refresh Token, API Secret, 개인키 및 서비스 계정 원문을 소스, 문서, 로그 및 예시에 기록하지 않는다.
- 실제 사용자 식별값, 이메일, 전화번호, OAuth 식별값 및 운영 데이터를 테스트나 문서 예시에 사용하지 않는다.
- 외부 입력을 SQL 식별자, 경로, 명령 또는 URL에 사용할 때 허용 목록과 경계를 검증한다.
- 삭제, 덮어쓰기, 이동 및 배포처럼 복구가 어려운 작업은 정확한 대상을 먼저 확인한다.
- 사용자에게 원시 예외, 내부 경로, 스택 트레이스 및 비밀 설정을 노출하지 않는다.

### CORE-INTEGRITY-001 데이터와 상태 무결성

- 외부 입력, DB 조회 결과 및 외부 API 응답은 사용 전에 유효성을 검증한다.
- 여러 상태 변경이 하나의 업무 처리를 이루면 일부 실패 시 전체 정합성이 유지되도록 트랜잭션 또는 보상 경계를 둔다.
- 성공, 실패, 재시도, 중복 요청 및 동시성 경로를 함께 검토한다.
- 클라이언트 입력만 신뢰하지 않고 권한과 공개 범위는 서버에서 다시 결정한다.
- 검증하지 못한 경로와 잔여 위험을 완료 결과에서 숨기지 않는다.

### CORE-FUNCTIONAL-001 loc 기능 테스트

- 사용자 기능을 구현하거나 실행 결과에 영향을 주는 변경은 가능한 경우 `application-loc.yml` 환경의 실행 서버에서 실제 화면으로 검증한다.
- 인증이 필요한 기능은 `/api/oauth/local-login?userNumb={userNumb}` 간편 로그인 URL을 사용하고 localhost와 Tailnet 중 현재 접근 가능한 주소에서 검증한다.
- 간편 로그인 테스트에는 1번과 2번 사용자를 사용하지 않고, 3번 이상의 활성 테스트 사용자 중 기능에 적합한 사용자를 선택한다.
- 사용자 간 상호작용은 서로 다른 로그인 세션으로 양쪽 화면을 확인하고 API 호출만으로 실제 화면 검증을 대체하지 않는다.
- 상태를 변경하는 테스트 데이터는 검증 후 원복하며, 팔로우 삭제처럼 정책상 복원되지 않거나 원복할 수 없는 영향은 실행 전에 범위를 제한하고 완료 결과에 기록한다.
- 간편 로그인과 테스트 사용자 접근은 `loc` 환경에서만 허용하며 운영 및 운영 데이터에는 적용하지 않는다.
- 화면이 없는 내부 기능, 실행 환경 장애 또는 복구 불가능한 위험 때문에 실제 화면 검증을 수행할 수 없으면 대체 검증을 실행하고 미실행 사유와 남은 위험을 완료 결과에 보고한다.

### CORE-COMMENT-001 소스 주석

- 소스 코드, 테스트 코드, 빌드·배포 스크립트 및 환경설정의 일반 주석과 API 문서 주석은 문장형 종결어미 없이 간결한 명사형으로 작성한다.
- 일반 주석과 API 문서 주석의 끝에는 `한다`, `이다`, `된다`, `있다`, `없다`, `않는다`와 존댓말형 `다`, `니다` 종결어미를 사용하지 않는다.
- 명사형 주석 끝에는 마침표를 사용하지 않는다.
- 주석에 존댓말, 이모티콘, 이모지, 느낌표 및 물음표를 사용하지 않는다.
- 코드가 무엇을 하는지 그대로 읽지 않고 구현 이유, 업무 정책, 실패 처리 및 경계 조건을 설명한다.
- 사용자에게 노출되는 실제 문구를 큰따옴표로 인용한 메시징 주석은 명사형과 문장부호 제한에서 제외하고 접두사 없이 원문을 그대로 작성한다.
- DDL `COMMENT`, 필드 설명 및 화면 영역명처럼 영역 규칙이 명사형을 요구하면 해당 예외를 적용한다.

### CORE-CONFIG-001 환경별 설정

- URL, 포트, 비밀값, 제한 건수, 만료 시간 및 스케줄처럼 환경에 따라 달라질 수 있는 값을 소스 코드에 하드코딩하지 않는다.
- 환경별 값은 YML 또는 환경변수로 관리하고 설정 바인딩을 통해 읽는다.
- 설정 키, 기본값 및 단위는 코드, YML, 예시 환경 파일, 배포 구성 및 운영 문서에서 일치시킨다.
- 브라우저 번들에는 공개해도 되는 설정만 전달한다.
- 운영에서 변경 가능성이 있는 정책값은 재빌드 없이 조정할 필요가 있는지 검토한다.

## 3. 계정 수명주기 정책

### CORE-ACCOUNT-001 구현 전 정책 게이트

- 새로운 기능을 추가하거나 기존 기능의 데이터 처리 범위를 확장하면 구현 전에 계정 비활성화와 영구 탈퇴 시 동작을 사용자에게 질문한다.
- 접근 제한, 공개 범위, 데이터 보존 또는 삭제, 복귀 시 복원 범위, 알림 및 소셜 관계 영향을 함께 결정한다.
- 확정한 내용은 같은 작업에서 `docs/policies/withdrawal-policy.md`, 해당 기능 정책 문서, 코드 및 테스트에 반영한다.
- 사용자가 확정하지 않은 항목은 기존 정책으로 임의 추정하거나 구현하지 않는다.
- 현재 계정 비활성화는 `WITHDRAWN` 상태이며 재로그인 시 `ACTIVE`로 전환하지만 비활성화 과정에서 비공개·삭제·중지된 독후감 공개 설정, 댓글, 알림 및 푸시 구독은 자동 복원하지 않는다.
- 현재 영구 탈퇴는 `DELETE_PENDING` 상태로 기본 30일 유예하며 유예기간 안에는 취소할 수 있고, 유예 후 물리 삭제한 계정과 데이터는 복구하지 않는다.
- `docs/policies/withdrawal-policy.md`를 계정 수명주기의 단일 기준 문서로 사용한다.

## 4. 규칙 유지보수와 완료

### CORE-MAINT-001 규칙 변경

- 재발 방지 기준이 필요하면 코드만 수정하지 않고 같은 작업에서 규칙을 갱신한다.
- 공통 기준은 이 문서에 한 번만 정의하고 영역 문서에서는 Core 규칙 ID를 참조한다.
- 영역 전용 기준은 가장 관련 있는 영역 문서의 기존 절을 확장한다.
- 새 규칙에는 고유하고 안정적인 규칙 ID, `MUST`·`SHOULD`·`MAY` 수준, 적용 대상, 예외 및 검증 방법을 기록한다.
- 새 항목을 만들기 전에 기존 규칙과 중복되거나 충돌하는지 확인한다.
- 규칙 변경 후 변경 문서를 다시 읽고 현재 작업 결과에도 즉시 적용한다.

### CORE-COMPLETE-001 완료 검사

- 변경 파일별로 활성 규칙 ID를 다시 대조한다.
- 기본 검증으로 `scripts/verify-project-rules.ps1`을 실행한다.
- Java 또는 프론트엔드 실행 결과에 영향을 주는 변경은 가능한 경우 `scripts/verify-project-rules.ps1 -Full`을 실행한다.
- 자동 검사만으로 확인할 수 없는 정책, 화면, 트랜잭션 및 문서 사실성은 수동으로 검토한다.
- 실패한 검사를 수정하지 않은 채 성공으로 보고하지 않는다.

### CORE-REPORT-001 완료 보고

최종 결과에는 다음 내용을 포함한다.

1. 변경 결과와 주요 파일
2. 적용한 주요 규칙 ID
3. 실행한 검증 명령과 결과
4. 실행하지 못한 검증과 남은 위험
