# 마이페이지 독서 요약 조회 성능 개선

## 개요

- 작업일: 2026-07-29
- 대상 화면: 마이페이지
- 대상 기능: 현재 읽고 있는 책, 기간별 독서량, 목표 달성 현황
- 대상 API: 마이페이지 독서 활동 요약 조회 API

마이페이지에서 프로필 정보는 먼저 표시되지만 현재 읽고 있는 책과 목표 달성 현황이 늦게 나타나는 문제가 있었다. 원인은 하나의 요약 응답을 만들기 위해 같은 독후감과 목표 데이터를 조건만 바꾸어 여러 번 조회하는 구조였다.

## 개선 전 문제

### 과도한 SQL 호출

기존 서비스는 주간, 월간, 연간 데이터를 각각 조회한 뒤 Java에서 하나의 응답으로 조립했다.

| 조회 목적 | 호출 횟수 |
| --- | ---: |
| 현재 및 이전 주, 월, 연도 독서량 | 6회 |
| 현재 및 이전 주, 월, 연도 목표 | 6회 |
| 주간, 월간, 연간 목표 달성 횟수 | 3회 |
| 현재 읽는 책과 주간, 월간, 연간 완료 목록 | 4회 |
| 합계 | 19회 |

한 번의 화면 요청에서 최대 19번의 SQL 왕복이 발생했다. 각 SQL의 실행 시간이 짧아도 애플리케이션과 DB 사이의 네트워크 왕복, 커넥션 사용, SQL 파싱 및 실행 비용이 누적되는 구조였다.

### 동일 테이블 반복 조회

독후감을 주간, 월간, 연간 조건으로 반복 조회했다. 현재 주의 완료 독후감은 현재 월과 현재 연도에도 포함되지만 각 목록을 별도로 조회하므로 같은 데이터를 여러 번 읽었다.

목표 달성 횟수도 주간, 월간, 연간 목표 유형마다 완료 독후감을 다시 집계했다. 독후감 수가 증가할수록 반복 스캔 비용도 함께 증가할 수 있었다.

### 초기 화면의 체감 지연

프로필 정보와 독서 활동 요약을 함께 기다리는 화면 구조에서는 요약 API가 느릴 때 프로필 영역까지 늦게 보이는 것처럼 느껴졌다. 조회 중인 영역에 별도 상태 표시가 없어 사용자는 화면이 멈춘 것으로 인식할 수 있었다.

## 개선 내용

### 집계 SQL 통합

기간별 독서량, 현재 및 이전 목표, 목표 수정 횟수, 누적 목표 달성 횟수를 `getReadingSummary` SQL 한 번으로 조회하도록 변경했다.

통합 SQL은 다음 CTE로 역할을 나누었다.

| CTE | 역할 |
| --- | --- |
| 완료 독후감 기준 집합 | 사용자의 완료 독후감을 한 번 조회하고 주간, 월간, 연간 목표 기준값 생성 |
| 기간별 독서량 집계 | 조건부 집계로 현재 및 이전 주, 월, 연도 독서량 계산 |
| 목표별 독후감 집계 | 완료 독후감을 목표 유형과 목표 기간별로 집계 |
| 목표 달성 요약 | 현재 및 이전 목표, 목표 수정 횟수, 누적 목표 달성 횟수 계산 |

`SUM(CASE WHEN ... THEN 1 ELSE 0 END)` 조건부 집계를 사용해 기간 조건마다 별도 SQL을 실행하지 않고 한 번의 결과 행으로 반환했다.

### 목록 SQL 통합

현재 읽는 책과 올해 완료한 책을 `getReadingSummaryList` SQL 한 번으로 조회하도록 변경했다.

서비스에서는 한 번 조회한 목록을 다음 기준으로 분류한다.

- `읽는 중` 상태는 현재 읽고 있는 책 목록에 포함
- `완독` 상태는 종료일을 기준으로 현재 주 목록에 포함
- `완독` 상태는 종료일을 기준으로 현재 월 목록에 포함
- `완독` 상태는 종료일을 기준으로 현재 연도 목록에 포함

서로 포함 관계인 주간, 월간, 연간 목록을 DB에서 각각 가져오지 않고 애플리케이션에서 한 번 순회해 구성한다. 조회 범위는 현재 읽는 책과 현재 연도 완료 도서로 제한해 불필요한 전체 이력 적재를 방지했다.

### 조회 전용 DTO 도입

`ReadingSummaryQueryDto`에 다음 값을 모아 통합 SQL의 입력 조건과 집계 결과를 전달하도록 구성했다.

- 사용자 번호
- 독서 상태 및 목표 유형 코드
- 본인 또는 다른 사용자 화면을 구분하는 선택적 독후감 공개 여부
- 현재 및 이전 주, 월, 연도 경계값
- 현재 및 이전 목표 기준값
- 기간별 독서량과 목표 집계 결과

서비스에서 기간을 한 번 계산하고 Mapper에는 명시적인 경계값을 전달하므로 여러 SQL에서 기간 계산이 달라지는 문제도 방지했다.

소셜 프로필은 별도 SQL을 만들지 않고 같은 집계와 목록 SQL에 `공개 여부 = 'Y'` 조건을 전달한다. 본인 마이페이지는 공개 여부 조건을 비워 기존 전체 독후감 범위를 유지하며, 소셜 프로필의 목표 데이터는 유지하되 총 읽은 책, 받은 좋아요, 독서량, 목표 달성 집계 및 목록에는 공개 독후감만 반영한다.

### 화면 조회 분리

프로필 조회와 독서 활동 요약 조회를 독립적으로 시작하도록 변경했다. 독서 활동 데이터가 준비될 때까지 별도의 로딩 영역을 만들지 않고, 조회 완료 후 결과를 페이드 인으로 표시한다.

이 변경은 DB 실행 시간을 직접 줄이는 작업은 아니지만 프로필 영역을 먼저 사용할 수 있게 해 체감 대기 시간을 줄인다.

| 집계 SQL | 15회 | 1회 |
| 목록 SQL | 4회 | 1회 |
| 목록 구성 | DB에서 기간별 반복 조회 | Java에서 한 번 순회 |

SQL 호출 수는 최대 19회에서 2회로 줄어 약 89.5% 감소했다. 이 수치는 SQL 왕복 횟수 감소율이며 실제 응답 시간 개선율은 데이터 건수, DB 부하, 네트워크 지연에 따라 달라진다.

| 비교 범위 | 본인 마이페이지의 기간 집계, 목표, 달성 횟수와 도서 목록 |
| 반복 방식 | 준비 10회 후 본 측정 100회, 개선 전·후 실행 순서를 반복마다 교대 |

개선 전 쿼리는 `74585d0` 커밋의 직전 버전에 있던 19회 호출 구조를 사용했다. 당시 SQL은 Oracle 문법이므로 `TO_DATE`, `NVL`, `TO_CHAR`만 현재 MySQL의 `STR_TO_DATE`, `COALESCE`, `DATE_FORMAT`으로 변환했다. 호출 횟수, 검색 조건, 조인, 정렬과 집계 의미는 변경하지 않았다. 개선 후 쿼리는 현재 `getReadingSummary`, `getReadingSummaryList` SQL을 사용했다.

측정 전에 두 구현이 반환한 다음 결과가 동일한지 확인했다.

- 현재·이전 주, 월, 연도 독서량 6개
- 현재·이전 주, 월, 연도 목표 6개
- 주간·월간·연간 누적 목표 달성 횟수 3개
- 현재 주, 월, 연도 완료 목록과 현재 읽는 목록 4개

### 측정 결과

| JDBC 전체 처리 시간 | 개선 전 19회 | 개선 후 2회 | 감소율 | 배수 |
| --- | ---: | ---: | ---: | ---: |
| 평균 | 264.725ms | 37.346ms | 85.89% | 7.09배 |
| 중앙값 | 215.241ms | 26.436ms | 87.72% | 8.14배 |
| P95 | 578.272ms | 80.201ms | 86.13% | 7.21배 |

같은 연결에서 `SELECT 1`로 측정한 단일 DB 왕복 시간은 평균 16.104ms, 중앙값 9.377ms, P95 42.670ms였다. 중앙값 기준으로 17회 감소한 왕복 비용만 약 159.409ms이므로, 관측한 188.805ms 차이의 대부분은 비로컬 DB 네트워크 왕복 축소로 설명할 수 있다.

`EXPLAIN ANALYZE`로 확인한 대표 쿼리의 DB 내부 실행 시간은 모두 1ms 미만이었다. 현재 목록 SQL은 업무 조회 최적화 인덱스로 독후감을 조회하고 도서 마스터는 기본키로 조인했다. 개선 전 기간 집계도 같은 사용자 인덱스를 사용했지만 `STR_TO_DATE(독서 종료일 또는 목표 종료일, ...)` 함수를 각 반복 쿼리에서 평가했다. 개선 전 주간 달성 집계는 독후감을 임시 집계한 뒤 목표 기본키와 조인했다.

### 해석과 제한

- 이 결과는 JDBC에서 19개 또는 2개 쿼리의 결과를 모두 소비할 때까지의 벽시계 시간이다.
- 개선 전 목표 상세 SQL은 결과 동등성에 필요한 목표 값만 조회해 역사적 DTO의 사용자 번호·기간·유형·수정 횟수 전송 비용을 포함하지 않았다. 따라서 개선 전 시간과 감소율을 실제 역사적 쿼리보다 작게 평가할 수 있는 보수적 조건이다.
- Spring MVC, MyBatis 객체 변환, HikariCP 대여, Service 목록 분류, JSON 직렬화와 브라우저 렌더링은 포함하지 않았다.
- 전체 독후감 11건인 작은 개발 DB이므로 데이터 증가 시 CTE, 정렬, 임시 집계와 애플리케이션 메모리 비용이 달라질 수 있다.
- 비로컬 DB의 왕복 지연이 포함되어 애플리케이션과 DB가 같은 네트워크에 있을 때보다 호출 횟수 감소 효과가 크게 나타날 수 있다.
- 준비 실행 이후의 결과이므로 최초 실행과 차가운 Buffer Pool 상태를 나타내지 않는다.
- 단일 연결의 순차 실행이며 동시 요청, HikariCP 경합과 DB 부하 증가는 측정하지 않았다.
- 운영 환경의 API 평균·P95·P99 응답 시간과 처리량을 의미하지 않는다.

## 격리 로컬 DB 더미 데이터 벤치마크

작은 개발 데이터셋의 한계를 보완하고 독서량·목표·목표 달성 횟수 데이터가 증가할 때의 변화를 확인하기 위해 별도의 로컬 MySQL 인스턴스에서 규모별 측정을 추가했다. 공유 개발 DB 계정은 임시 테이블 생성 권한이 없었으므로 해당 DB에는 데이터를 쓰지 않았고, 워크스페이스 안에 일회성 MySQL 8.4.10 데이터 디렉터리와 격리 스키마를 구성했다.

| 10,000건 | 329건 | 평균 | 321.774ms | 186.606ms | 42.01% | 1.72배 |
|  |  | 중앙값 | 314.315ms | 175.091ms | 44.29% | 1.80배 |
|  |  | P95 | 435.453ms | 269.750ms | 38.05% | 1.61배 |

### 해석과 제한

- 100건부터 10,000건까지 개선 후 구조가 모든 구간에서 빨랐고, 10,000건에서도 중앙값이 44.29% 감소했다.
- 로컬 루프백은 비로컬 개발 DB보다 왕복 지연이 작다. 데이터가 증가할수록 17회 왕복 제거의 상대적 이점보다 CTE 집계, 정렬과 통합 목록 결과 소비 비용의 비중이 커져 개선 배수는 2.64배에서 1.80배로 낮아졌다.
- 독후감은 최근 5년에 균등하게 분산된 합성 데이터이며 실제 사용자의 날짜 편중, 도서 다양성, 문자열 크기와 공개 범위 분포를 재현하지 않는다.
- 도서 한 권을 반복 참조하므로 도서 Buffer Pool 적중과 기본키 조인이 실제보다 유리할 수 있다. 반면 독후감 목록의 결과 행 소비와 제목 정규식 처리는 생략하지 않았다.
- 목표 수는 329건으로 고정하고 독후감만 늘렸으므로 목표 이력 자체가 대규모로 증가하는 상황은 별도 측정이 필요하다.
- 단일 연결의 준비된 상태를 측정했으며 동시 사용자, 차가운 Buffer Pool, 커넥션 풀 경합과 API 전체 응답 시간은 포함하지 않는다.
- 공유 개발 DB와 운영 테이블에는 더미 데이터를 삽입하지 않았고, 로컬 격리 스키마의 기준 테이블 행 수도 측정 전후 동일함을 확인했다.

## 고려한 사항

### 통합 SQL 복잡도

SQL 호출 수를 줄이는 대신 CTE와 조건부 집계가 추가되어 쿼리가 복잡해졌다. 각 CTE가 독후감 원본 조회, 기간 집계, 목표 집계 역할을 분리하도록 구성해 유지보수 범위를 명확히 했다.

### 애플리케이션 메모리 사용

목록 분류를 Java에서 처리하므로 조회 결과를 메모리에 보관한다. 전체 독후감 이력이 아니라 현재 읽는 책과 현재 연도 완료 목록만 조회해 메모리 사용 범위를 제한했다.

### 날짜 비교

독서 종료일은 `YYYY-MM-DD` 형식이므로 Java 목록 분류에서는 문자열의 사전 순서와 날짜 순서가 같다는 점을 이용했다. 형식이 변경되면 `LocalDate` 변환 방식으로 함께 수정해야 한다.

## 운영 환경 추가 측정 항목

실제 운영 성능을 확인하려면 운영과 유사한 데이터 건수와 동시 요청 조건에서 다음 값을 개선 전후 비교해야 한다.

1. Spring Boot API 전체 평균·중앙값·P95·P99 응답 시간
2. 독후감과 목표 건수를 단계적으로 늘린 실행 계획과 논리 읽기 변화
3. 동시 요청 증가 시 HikariCP 커넥션 사용량과 대기 시간
4. 애플리케이션 목록 분류의 CPU와 메모리 사용량
5. 운영과 같은 네트워크 배치에서의 DB 왕복 시간과 처리량
