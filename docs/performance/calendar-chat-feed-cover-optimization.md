# 캘린더·채팅·피드·표지 분석 성능 개선

2026-11-26 로컬 개발환경에서 네 가지 리팩토링을 구현하고, 동일한 개발 데이터로 변경 전후를 비교했다. 캘린더와 피드의 기존 응답은 유지하고, 채팅은 새 본문과 기존 미읽음 수를 분리했다. 로컬 검증 후 같은 날 운영 배포까지 완료했으며 배포 확인 범위는 아래에 별도로 기록했다.

## 측정 결과

아래 시간은 브라우저 렌더링 시간이 아닌 실제 API 요청의 서버 처리 시간이다. 요청은 Tailnet HTTPS 주소를 통해 실행했고, 공통 요청 로그의 원본 소요시간으로 다시 집계했다. 중앙값은 짝수 표본의 가운데 두 값을 평균했으며, p95는 nearest-rank 방식으로 계산했다. 표본 10개의 p95는 최댓값이므로 안정적인 운영 p95 추정값으로 해석하지 않는다.

| --- | ---: | ---: | ---: | ---: | ---: |

표지는 같은 실제 외부 표지를 여섯 번 순차 요청했다. 첫 요청은 내려받기와 분석을 포함하며, 이후 다섯 번의 재요청을 비교했다.

최초 표지 분석이 빨라졌다고 해석하지 않는다. 개선 대상은 성공한 동일 표지의 재요청이다. 재요청 중앙값 감소율은 86.7%이며, 모든 요청의 색상 응답은 변경 전후에 같았다.

## 측정 조건

- Windows, Java 17, Spring Boot 4.0.3의 로컬 프로필, 기존 개발 MySQL과 Redis를 사용했다.
- 동일 PC에서 백엔드와 Vite를 실행하고 Tailnet HTTPS 프록시를 통해 호출했다. 운영 DB는 사용하지 않았다.
- 별도 표식이 있는 독후감 3,000건과 각 독후감의 좋아요·댓글 한 건씩을 생성했다. 기존 테스트 회원의 기록 한 건을 포함해 캘린더 조회 대상 회원의 전체 기록은 3,001건이었다.
- 생성한 독후감 중 2,900건은 과거 기간, 100건은 조회 월에 배치했다. 달력 표시 범위의 응답은 기존 기록을 포함해 101건이었다.
- 별도 테스트 모임에 활성 테스트 회원 두 명과 채팅 100건을 구성했다. 성능 측정 뒤의 기능 테스트 메시지는 시간 비교 표본에 포함하지 않았다.
- 캘린더, 피드, 채팅 조회, 열람 갱신은 각각 예열 2회 이후 10회씩 순차 측정했다. 변경 전후에 같은 데이터와 요청 조건을 사용했다.
- 채팅의 변경 전 요청은 기존 최근 메시지 조회이며, 변경 후 요청은 새 메시지와 기존 미읽음 수의 동기화 조회다. 반환 본문이 줄어드는 유휴 폴링 업무를 비교한 것이다.
- 잘못된 테스트용 화면 식별값이나 요청 제한시간 때문에 완료되지 않은 예비 실행은 최종 표본에 포함하지 않았다. 최종 비교에는 성공한 완결 실행의 표본만 사용했다.

개발 PC 상태, DB 캐시, Tailnet 지연과 순차 실행 순서가 결과에 영향을 줄 수 있다. 동시 부하 처리량, CPU·메모리 사용량, 실행계획의 실제 스캔 수와 운영 성능은 측정하지 않았다.

## 캘린더 조회

변경 전에는 회원의 전체 독후감 목록을 조회한 뒤 Java에서 달력의 42일과 겹치는 기록을 골랐다. 이 과정에서 달력에 쓰지 않는 본문과 여러 코드명도 조회했다.

변경 후에는 Mapper가 인증 사용자와 표시 기간으로 후보를 좁히고, 독후감 번호·제목·시작일·종료일·색상만 반환한다. 기간을 좁힌 후보에도 기존 날짜 파싱과 중첩 판정을 적용해 잘못된 과거 날짜의 제외 기준을 유지했다. 호출자가 없어진 전체 목록 Service 메서드는 제거했다.

DB가 애플리케이션에 반환한 기록은 3,001건에서 101건으로 감소했다. 이는 실제 스캔 행 수나 인덱스 효율을 측정한 수치가 아니다. 날짜 저장 구조와 인덱스는 변경하지 않았다.

구현 근거는 `MyPageController.getReadingCalendar`, `ReportServiceImpl.getReadingCalendar`, `ReportMapper.getReadingCalendar`, `ReadingCalendarDto`다. 응답의 모든 항목과 필드, 정렬 순서가 변경 전과 정확히 일치하는지 실제 API로 비교했다.

## 채팅 동기화

기존 화면은 3초마다 최근 메시지 최대 100건을 다시 받았다. 같은 읽음 위치를 반복 전송해도 모임 공용 행을 잠그고 읽음 위치와 관련 알림을 갱신했다.

변경 후 최초 조회는 기존 경로를 사용하고, 이후 `/api/reading-clubs/{clubNumb}/chats/sync`에서 새 메시지 본문과 기존 최근 100건의 미읽음 수만 받는다. 기존 메시지의 숫자만 갱신하므로 새 메시지가 없어도 다른 회원의 읽음 상태를 반영한다. 변경 없는 응답은 기존 React 배열 참조를 유지한다.

읽음 위치가 실제로 전진한 경우에만 기존 쓰기 트랜잭션과 모임 행 잠금을 사용한다. 열람 유효시간 갱신과 화면 종료 신호는 현재 모임·계정·회원 권한을 검사하되 공용 행 잠금과 읽음 상태 갱신을 수행하지 않는다. 숨김 전환이나 요청 실패로 전송하지 못한 읽음 위치는 확정하지 않고 다음 폴링에서 재시도한다.

- 새 메시지가 없는 조회의 JSON 응답은 33,935바이트에서 3,084바이트로 90.9% 감소했다. 압축 전 JSON 바이트 수이며 TLS 전송량은 아니다.
- 일반적인 유휴 주기의 업무 Mapper 호출 수는 소스 기준 7회에서 5회로 감소한다. 조회 자체는 기존 2회에서 3회가 되고, 열람 갱신은 기존 5회에서 2회가 된다. 인증 공통 처리의 조회는 이 계산에서 제외했다.
- 유휴 열람 갱신의 공용 행 잠금은 1회에서 0회, 읽음 관련 DML은 2회에서 0회가 된다. 이는 소스와 모의 객체 호출 검증으로 확인한 구조 차이다.
- 폴링 간격과 정상 유휴 주기의 HTTP 요청 두 번은 유지했다. 요청 횟수를 줄인 결과로 설명하지 않는다.

구현 근거는 `useClubChatPage`, `mergeChatMessages`, `ReadingClubServiceImpl.getClubChatSync`, `ReadingClubServiceImpl.uptClubChatRead`, `ReadingClubMapper.getChatReadCounts`다.

## 피드 집계

기존 쿼리는 페이지 대상 제한이 없는 좋아요·댓글 집계에 피드를 결합한 뒤 최종 단계에서 페이지를 잘랐다.

변경 후에는 기존 공개·팔로우·차단 조건과 활동 정렬 기준을 적용한 뒤 먼저 최대 11건을 선택한다. 좋아요·댓글 집계는 선택한 대상에만 연결하고, 표시용 코드명도 해당 페이지에서 계산한다. 화면에 10건과 다음 페이지 여부를 반환하는 계약은 유지했다.

페이지 후보를 위한 CTE가 추가되므로 작은 데이터에서도 항상 유리하다고 단정할 수 없다. 좋아요순 정렬을 사용하는 다른 목록에 그대로 적용해서는 안 되며, 이번 변경은 활동 시간순 피드에 한정했다. 사용자 사진이나 독후감의 현재 공개 조건과 차단 집계 제외 조건도 유지했다.

구현 근거는 `FeedMapper.getFeedList`, `FeedServiceImpl.getFeedList`다. 실제 첫 페이지의 응답이 변경 전과 정확히 일치하는지 비교하고, 화면에서 좋아요·댓글 수가 각각 유지되는지 확인했다.

## 표지 대표색 캐시

성공한 표지의 대표 RGB만 프로세스 메모리에 저장한다. 원본 이미지와 사용자 정보, 최종 색상 코드는 보관하지 않는다. 현재 활성 색상 코드는 매 요청에 다시 조회하고 RGB와 매칭하므로 코드 변경 후에도 오래된 선택 결과를 재사용하지 않는다.

캐시 기본값은 유효시간 900초, 최대 256항목이다. 같은 표지의 동시 요청은 고정된 해시 잠금을 공유하고, 전체 캐시 잠금은 네트워크 대기 중 보유하지 않는다. 다른 URL이 같은 해시 버킷에 들어가면 잠시 직렬화될 수 있다. 캐시가 가득 차면 가장 먼저 저장된 항목부터 제거한다.

허용 호스트·HTTPS·리다이렉트 차단·이미지 바이트 및 픽셀 제한은 기존 다운로드 경로를 유지한다. 다운로드 또는 디코딩 실패와 유효한 대표색이 없는 결과는 캐시하지 않는다. 서버 재시작과 유효시간 만료 뒤에는 다시 분석하며, 여러 서버 사이의 캐시는 공유하지 않는다.

`BOOK_COVER_COLOR_CACHE_SECONDS`, `BOOK_COVER_COLOR_CACHE_MAX_ENTRIES`를 운영 YML, 예시 환경 파일, Actions 변수 전달과 [운영 배포 문서](../github-actions-deployment.md)에 함께 반영했다. 두 설정 중 하나가 0 이하면 캐시 저장을 생략한다.

구현 근거는 `BookCoverColorService.getCachedCoverRgb`, `BookCoverColorService.getNearestBookColor`다. 실제 화면에서 동일 도서를 두 번 선택한 결과 대표색 API 두 번에 분석 완료 로그는 한 번이었다. 동시 요청 공유·항목 상한·만료·실패 재시도·팔레트 변경은 별도 테스트로 검증했다.

## 운영 배포 확인

2026-11-26 22:22 KST 기준 애플리케이션 커밋 `c42df32a48998be9ec48451d87770dfa2bb2b866`의 [운영 CI/CD 실행](https://github.com/hwaiplay/sadari/actions/runs/45825570612)이 성공했다. 빌드 검증, AMD64·ARM64 이미지 게시, Mac mini 배포와 서버 내부 HTTP 헬스 체크를 모두 통과했다. 별도로 작업 중인 Docker·CI 산출물 재사용 변경은 이번 배포에 포함하지 않았다.

- 운영 HTTPS 진입 페이지와 새 정적 번들 응답의 HTTP 200 확인
- 배포 전후 진입 번들 식별값 변경과 채팅 증분 API 호출 코드 반영 확인
- 인증 없는 피드 요청의 HTTP 401 응답과 브라우저 로그인 화면 표시 확인
- 배포 로그에서 표지 캐시 설정의 유효시간 900초와 최대 256항목 전달 확인
- 이번 변경에 따른 DB 구조 변경과 데이터 마이그레이션 없음

운영 계정으로 로그인한 이후의 기능 테스트와 운영 부하·성능 비교는 수행하지 않았다. 앞의 성능 수치는 로컬 개발환경의 변경 전후 측정값이다. 복구가 필요하면 [운영 배포 절차](../github-actions-deployment.md)의 이전 이미지 복구 경로를 사용하며, 별도 DB 역마이그레이션은 필요하지 않다.
