# 고객문의 및 관리자 답변 기능 설계

## 개요

- 기준일: 2026년 8월 13일
- 문서 상태: 1차 적용
- 적용 서비스: 사용자 서비스 `sadari`, 관리자 서비스 `sadari-admin`
- 목적: 비공개 고객문의 접수, 관리자 답변, 이용정지 이의제기 및 제재 해제 연계 기준을 정의한다.

사용자 및 관리자 화면, API, 테이블과 권한 경로를 1차 범위로 구현했다. 계정 수명주기 기준은 [고객문의 및 관리자 답변 정책](../policies/customer-inquiry-policy.md)을 단일 기준으로 적용한다.

## 확정 요구사항

1. 고객문의와 관리자 답변을 1차 개발 범위에 함께 포함한다.
2. 문의 카테고리에 이용정지에 대한 이의와 불만을 포함한다.
3. 이용정지 회원도 같은 Kakao 계정으로 로그인한 제한 인증 상태에서 본인 문의를 등록하고 답변을 확인할 수 있다.
4. 관리자 답변 등록과 이용정지 해제는 서로 다른 업무로 처리한다.
5. 이용정지 이의 문의는 문의 대상인 정확한 `TH_USSPND.SPND_NUMB`와 연결한다.
6. 고객문의는 기존 사용자 및 콘텐츠 신고 기능인 `TH_CMPLNT`와 분리한다.
7. 관리자 메뉴는 `사용자 관리 > 고객문의 관리`에 배치하고 기준 경로로 `/sadari/adm/inquiry`를 사용한다.
8. 사용자 메뉴는 햄버거 메뉴에 배치하고 목록 기준 경로로 `/inquiry/list`를 사용한다.

## 설계 원칙

- 고객문의는 작성자와 권한 있는 관리자만 조회하는 비공개 데이터이다.
- 사용자 요청의 `USER_NUMB`를 신뢰하지 않고 인증 정보에서 작성자 번호를 결정한다.
- 답변을 등록해도 이용정지를 자동 해제하지 않는다.
- 제재 해제는 권한 확인, 해제 사유 입력 및 감사 이력 저장을 거치는 별도 작업이다.
- 관리자 내부 정지 메모와 해제 메모는 사용자 응답에 포함하지 않는다.
- 탈퇴 후 새로 가입한 계정에 과거 문의와 답변을 자동 연결하지 않는다.
- 답변 알림과 푸시는 보조 수단이며 고객문의 상세 조회를 최종 확인 수단으로 사용한다.

## 개발 범위

### 1차 개발 범위

사용자 서비스에는 다음 기능을 추가한다.

- 고객문의 목록 조회
- 고객문의 등록
- 고객문의 상세 및 관리자 답변 조회
- 미확인 답변 표시와 확인 처리
- 이용정지 화면의 이의신청 진입
- 정지 회원에게 허용할 고객문의 화면 및 API 예외 처리

관리자 서비스에는 다음 기능을 추가한다.

- 고객문의 목록과 검색
- 고객문의 상세 조회
- 담당자 지정과 검토 시작
- 관리자 답변 등록
- 최초 관리자 답변 등록
- 연결된 이용정지 이력 조회
- 기존 이용정지 해제 서비스 연결
- 관리자 메뉴별 읽기 및 쓰기 권한 적용

### 1차 제외 범위

- 파일 및 이미지 첨부
- 사용자의 문의 등록 후 추가 메시지
- 이메일 상담
- 실시간 채팅
- 문의 삭제
- 공개된 답변의 수정 및 삭제
- 자동 답변과 상담 챗봇
- 운영자 내부 메모
- 답변 알림과 FCM 푸시
- 정지 회원 영구탈퇴와 탈퇴 뒤 Kakao 계정 제재 유지 및 관리자 해제

사용자의 추가 메시지가 필요해지면 관리자 답변 전용 테이블을 확장하기보다 작성자 유형을 포함하는 별도의 문의 메시지 구조를 검토한다.

## 메뉴와 화면 경로

### 사용자 화면

| 화면 | 경로 | 상태 | 설명 |
| --- | --- | --- | --- |
| 고객문의 목록 | `/inquiry/list` | 확정 | 햄버거 메뉴에서 진입하는 기준 화면 |
| 고객문의 등록 | `/inquiry/write` | 확정 | 일반 문의 및 이용정지 이의 문의 등록 |
| 고객문의 상세 | `/inquiry/detail/:inqrNumb` | 확정 | 본인 문의와 답변 내역 조회 |
| 이용정지 안내 | `/suspension` | 현행 | 고객문의 등록과 목록 진입 버튼 추가 예정 |

정지 회원은 `/suspension`, `/inquiry/list`, `/inquiry/write`, `/inquiry/detail/:inqrNumb`만 제한적으로 이동할 수 있다. 일반 서비스 경로 접근은 계속 차단한다.

`ACTIVE` 회원의 고객문의 화면은 사용자 서비스의 공통 헤더와 하단 네비게이션을 그대로 사용한다. `SUSPENDED` 회원은 일반 서비스 메뉴를 노출하지 않고 공통 헤더 규격과 동일한 문의 헤더 및 `정지 안내`, `문의 내역`, `문의하기`만 제공하는 제한 하단 네비게이션을 사용한다. 목록, 작성, 상세 화면은 공지사항과 설정 화면의 여백, 테두리, 타이포그래피 및 상태 색상 체계를 따른다.

### 관리자 화면

| 화면 | 경로 | 상태 | 설명 |
| --- | --- | --- | --- |
| 고객문의 관리 | `/sadari/adm/inquiry` | 확정 | `사용자 관리` 하위 메뉴의 문의 목록 |
| 고객문의 상세 | `/sadari/adm/inquiry/detail/:inqrNumb` | 확정 | 문의, 답변 및 연결 제재 조회 |

관리자 메뉴에는 읽기와 쓰기 권한을 적용한다. 고객문의 쓰기 권한은 답변과 담당자 변경에 사용하며, 이용정지 해제는 기존 현재 사용자 관리의 제재 해제 권한을 다시 검증한다.

## 문의 카테고리

문의 카테고리는 `INQR_CATG` 공통코드로 관리한다.

| 상세코드 | 표시명 | 설명 |
| --- | --- | --- |
| `GENERAL` | 일반 문의 | 서비스 이용에 대한 일반 문의 |
| `ACCOUNT` | 계정 문의 | 로그인과 계정 상태에 대한 문의 |
| `SUSPENSION_APPEAL` | 이용정지 이의제기 | 정지 사유 이의, 오정지 주장 및 해제 요청 |
| `BUG` | 오류 신고 | 화면 또는 기능 오류 문의 |
| `SUGGESTION` | 제안 | 서비스 개선 제안 |

`SUSPENSION_APPEAL` 문의는 서버가 로그인 회원의 활성 이용정지를 조회하여 `SPND_NUMB`를 자동 연결한다. 일반 문의의 `SPND_NUMB`는 `NULL`이다.

## 문의 상태

문의 처리 상태는 `INQR_STAT` 공통코드로 관리한다.

| 상세코드 | 표시명 | 의미 |
| --- | --- | --- |
| `INQR_RECEIVED` | 접수 | 담당자가 지정되지 않은 최초 상태 |
| `INQR_REVIEWING` | 검토 중 | 담당 관리자가 지정되어 검토하는 상태 |
| `INQR_ANSWERED` | 답변 완료 | 사용자에게 공개된 답변이 한 건 이상 존재하는 상태 |

기본 상태 흐름은 다음과 같다.

```text
INQR_RECEIVED -> INQR_REVIEWING -> INQR_ANSWERED
```

- 문의 상세 조회만으로 상태를 변경하지 않는다.
- 관리자가 명시적으로 검토를 시작할 때 담당자와 `INQR_REVIEWING`을 저장한다.
- 담당자를 해제하면 답변이 없는 문의만 `INQR_RECEIVED`로 되돌릴 수 있다.
- 첫 답변을 등록하면 `INQR_ANSWERED`로 변경한다.
- 정정 답변을 추가하면 상태는 `INQR_ANSWERED`로 유지한다.

## 데이터 구조

### 고객문의 `CT_INQURY`

`CT_INQURY`는 사용자가 등록한 최초 문의와 현재 처리 상태를 저장하는 사용자 노출 운영 콘텐츠 테이블이다.

| 순서 | 컬럼 | 적용 타입 | Null | 설명 |
| ---: | --- | --- | --- | --- |
| 1 | `INQR_NUMB` | `bigint` | N | 문의 번호 |
| 2 | `USER_NUMB` | `bigint` | Y | 등록 시 필수이며 회원 물리 삭제 정책에 따라 제거할 수 있는 작성자 번호 |
| 3 | `INQR_CATG` | `varchar(20)` | N | `INQR_CATG` 상세코드 |
| 4 | `INQR_TITL` | `varchar(200)` | N | 문의 제목 |
| 5 | `INQR_CNTN` | `text` | N | 문의 내용 |
| 6 | `INQR_STAT` | `varchar(20)` | N | `INQR_STAT` 상세코드 |
| 7 | `SPND_NUMB` | `bigint` | Y | 이용정지 이의 문의가 대상으로 하는 정지 이력 번호 |
| 8 | `ASGN_ADMN` | `bigint` | Y | 담당 관리자 번호 |
| 9 | `ANSW_DATE` | `datetime(6)` | Y | 최근 답변 등록 일시 |
| 10 | `REGI_DATE` | `datetime(6)` | N | 문의 등록 일시 |
| 11 | `UPDT_DATE` | `datetime(6)` | N | 상태 또는 담당자 수정 일시 |

적용 인덱스는 다음과 같다.

| 이름 | 컬럼 | 목적 |
| --- | --- | --- |
| `IX_CT_INQURY_USER` | `USER_NUMB`, `REGI_DATE`, `INQR_NUMB` | 사용자별 문의 목록 |
| `IX_CT_INQURY_STAT` | `INQR_STAT`, `REGI_DATE`, `INQR_NUMB` | 관리자 처리 대기 목록 |
| `IX_CT_INQURY_ASGN` | `ASGN_ADMN`, `INQR_STAT`, `REGI_DATE` | 담당자별 문의 목록 |
| `IX_CT_INQURY_SPND` | `SPND_NUMB`, `INQR_STAT`, `REGI_DATE` | 제재별 이의 문의 조회 |

`SPND_NUMB`는 재가입 차단에 사용하는 값이 아니라 문의가 대상으로 한 정확한 제재 건을 보존하기 위한 업무 참조값이다. 재가입 차단은 `TH_USWTHD`의 보존 식별값과 `TH_USSPND`의 활성 제재를 이용한다.

### 고객문의 답변 `CT_INQANS`

`CT_INQANS`는 사용자에게 공개한 관리자 답변을 등록 순서대로 저장한다. 한 문의에 여러 답변을 등록할 수 있다.

| 순서 | 컬럼 | 적용 타입 | Null | 설명 |
| ---: | --- | --- | --- | --- |
| 1 | `ANSW_NUMB` | `bigint` | N | 답변 번호 |
| 2 | `INQR_NUMB` | `bigint` | N | 문의 번호 |
| 3 | `ANSW_CNTN` | `text` | N | 사용자에게 공개할 답변 내용 |
| 4 | `READ_YSNO` | `varchar(1)` | N | 사용자 확인 여부 |
| 5 | `READ_DATE` | `datetime(6)` | Y | 사용자 확인 일시 |
| 6 | `REGI_ADMN` | `bigint` | N | 답변 관리자 번호 |
| 7 | `REGI_DATE` | `datetime(6)` | N | 답변 등록 일시 |

적용 인덱스는 다음과 같다.

| 이름 | 컬럼 | 목적 |
| --- | --- | --- |
| `IX_CT_INQANS_INQR` | `INQR_NUMB`, `REGI_DATE`, `ANSW_NUMB` | 문의별 답변 내역 |
| `IX_CT_INQANS_READ` | `INQR_NUMB`, `READ_YSNO`, `REGI_DATE` | 문의별 미확인 답변 조회 |

공개된 답변은 수정하거나 삭제하지 않는다. 잘못된 답변은 추가 정정 답변으로 바로잡아 사용자에게 공개된 이력을 유지한다.

### 데이터 관계

```text
TM_USERXM 1 ----- N CT_INQURY 1 ----- N CT_INQANS
                       |
                       +----- 0..1 TH_USSPND
                       |
                       +----- 0..1 TM_ADMINX
```

- `CT_INQURY.USER_NUMB`는 `TM_USERXM`을 참조하며 회원 물리 삭제 시 `ON DELETE SET NULL`로 작성자 연결만 제거한다.
- `CT_INQURY.SPND_NUMB`는 영구 보존되는 `TH_USSPND.SPND_NUMB`를 참조할 수 있다.
- `CT_INQANS.INQR_NUMB`는 `CT_INQURY.INQR_NUMB`를 참조한다.
- 담당자와 답변 등록자는 실제 관리자 계정만 저장한다.

## 사용자 업무 흐름

### 일반 문의 등록

1. 사용자가 햄버거 메뉴의 고객문의를 선택한다.
2. `/inquiry/list`에서 본인 문의 목록을 조회한다.
3. 문의 등록 화면에서 카테고리, 제목과 내용을 입력한다.
4. 서버가 카테고리 공통코드와 입력 길이를 검증한다.
5. 서버가 인증 회원번호를 작성자로 사용해 `CT_INQURY`를 `INQR_RECEIVED` 상태로 등록한다.
6. 등록 완료 후 문의 상세 화면으로 이동한다.

### 이용정지 이의 문의 등록

1. 정지 회원이 같은 Kakao 계정으로 로그인한다.
2. 서버가 인증을 유지하면서 일반 서비스 대신 `/suspension`으로 이동시킨다.
3. 사용자가 `이용정지 이의신청`을 선택한다.
4. 문의 카테고리를 `SUSPENSION_APPEAL`로 고정하거나 기본 선택한다.
5. 서버가 로그인 회원의 `ACTIVE` 정지 이력을 조회한다.
6. 문의와 정확한 `SPND_NUMB`를 함께 저장한다.
7. 사용자는 제한 화면에서 문의 상태와 답변을 조회한다.

회원 상태가 `SUSPENDED`인데 활성 정지 이력이 없는 데이터 불일치 상황에서도 문의 등록은 허용한다. 이 경우 `SPND_NUMB` 없이 접수하고 관리자 화면에 상태 불일치 안내를 표시한다.

### 답변 확인

1. 사용자가 고객문의 목록에서 `답변 완료` 또는 미확인 표시를 확인한다.
2. 문의 상세에서 답변을 조회한다.
3. 화면 표시가 성공한 답변만 확인 API로 전달한다.
4. 서버가 문의 소유권을 검증한 뒤 `READ_YSNO`와 `READ_DATE`를 갱신한다.

정지 회원도 같은 흐름을 사용하며 일반 서비스 화면은 계속 차단한다.

## 정지 회원 접근 제어

정지 회원에게는 로그인 자체를 막지 않고 제한된 인증 상태를 제공한다. 사용자는 정지 안내, 본인 고객문의와 로그아웃만 이용할 수 있다.

1차 허용 API는 다음과 같다.

| Method | API | 용도 |
| --- | --- | --- |
| `GET` | `/api/user/suspension` | 현재 정지 정보 조회 |
| `GET` | `/api/inquiries` | 본인 문의 목록 조회 |
| `POST` | `/api/inquiries` | 본인 문의 등록 |
| `GET` | `/api/inquiries/{inqrNumb}` | 본인 문의와 답변 조회 |
| `PATCH` | `/api/inquiry-answers/{answNumb}/read-status` | 본인 답변 확인 처리 |
| `POST` | `/api/oauth/logout` | 로그아웃 |

인증 필터는 경로와 HTTP Method를 함께 확인한다. `/api/inquiries/**` 전체를 무조건 허용하지 않는다.

문의 상세와 답변 확인 SQL에는 인증 회원번호를 반드시 포함한다.

```sql
WHERE INQR_NUMB = #{inqrNumb}
  AND USER_NUMB = #{loginUserNumb}
```

## 관리자 업무 흐름

### 문의 검토

1. 관리자가 `사용자 관리 > 고객문의 관리`로 이동한다.
2. 상태, 카테고리, 담당자, 사용자 및 기간으로 목록을 검색한다.
3. 관리자가 상세 화면에서 문의와 작성자 상태를 확인한다.
4. 관리자가 `검토 시작`을 실행하면 자신을 담당자로 지정하고 상태를 `INQR_REVIEWING`으로 변경한다.

관리자 상세 화면의 단순 조회는 상태와 담당자를 변경하지 않는다.

### 답변 등록

한 트랜잭션에서 다음 작업을 처리한다.

1. 현재 문의 상태와 담당자를 잠금 조회한다.
2. 답변 등록 권한과 담당자를 검증한다.
3. `CT_INQANS`에 미확인 답변을 등록한다.
4. `CT_INQURY.INQR_STAT`을 `INQR_ANSWERED`로 변경한다.
5. `CT_INQURY.ANSW_DATE`와 `UPDT_DATE`를 갱신한다.
6. 답변 알림과 FCM 푸시는 1차에서 생성하지 않고 후속 개발로 둔다.

### 이용정지 해제

이용정지 이의 문의에는 연결된 제재 정보와 별도의 `이용정지 해제` 버튼을 제공한다.

1. 관리자가 현재 `SPND_STAT`을 다시 조회한다.
2. 관리자 제재 해제 권한을 검증한다.
3. 관리자에게 해제 사유를 입력받고 최종 확인을 받는다.
4. `TH_USSPND.SPND_STAT`을 `RELEASED`로 변경한다.
5. `RLES_DATE`, `RLES_ADMN`과 `RLES_CNTN`을 기록한다.
6. 회원 원본이 존재하면 계정 상태 우선순위에 따라 상태와 동기화 이벤트를 처리한다.
7. 회원 원본이 물리 삭제된 Kakao 계정의 제재 해제는 2차 회원 탈퇴정책 기능으로 처리한다.

답변 등록과 제재 해제는 별도 트랜잭션이다. 답변 문구만으로 제재가 해제되거나 제재 해제만으로 답변이 자동 생성되지 않는다.

## 관리자 화면 구성

### 목록 화면

검색 조건은 다음과 같다.

- 문의 번호
- 사용자 번호 또는 닉네임
- 문의 카테고리
- 처리 상태
- 담당 관리자
- 접수 기간
- 답변 미등록 여부

목록에는 다음 값을 표시한다.

- 문의 번호
- 카테고리
- 제목
- 사용자
- 현재 회원 상태
- 문의 상태
- 담당 관리자
- 접수 일시
- 최근 답변 일시

### 상세 화면

상세 화면은 다음 영역으로 구성한다.

1. 문의 정보
2. 작성자와 현재 계정 상태
3. 관리자 답변 내역
4. 답변 등록
5. 연결 이용정지 정보
6. 이용정지 해제

사용자에게 공개하는 답변과 관리자 내부 제재 메모를 시각적으로 분리한다. 관리자 내부 메모가 사용자 답변 입력란에 자동 복사되지 않도록 한다.

## 입력과 출력 정책

- 문의 제목은 최대 200자로 제한한다.
- 문의 본문과 답변은 UTF-8 기준 최대 4,000바이트로 제한한다.
- 제목, 문의 본문과 답변의 앞뒤 공백을 제거한다.
- HTML을 업무 데이터로 허용하지 않고 일반 텍스트로 저장한다.
- 화면에서는 스크립트나 HTML이 실행되지 않도록 안전한 텍스트로 표시한다.
- 고객문의는 비공개 상담이므로 공개 콘텐츠용 비속어 등록 차단을 적용하지 않는다.
- 동일 제재에 대해 `INQR_RECEIVED` 또는 `INQR_REVIEWING`인 이의 문의가 있으면 중복 등록을 제한한다.
- 제출 중에는 중복 요청과 화면 이탈을 차단하는 공통 처리 중 모달을 표시한다.

## 답변 확인과 후속 알림

1차에서는 답변 알림과 FCM 푸시를 생성하지 않는다. 사용자는 `/inquiry/list`의 미확인 답변 수와 상세 화면으로 답변을 확인한다.

후속 답변 알림에는 문의 본문이나 답변 내용을 포함하지 않는다.

제안 문구는 다음과 같다.

```text
고객문의에 답변이 등록되었습니다.
```

- 일반 회원의 알림 링크는 해당 고객문의 상세 화면으로 연결한다.
- 정지 회원은 일반 알림 화면을 이용할 수 있다고 가정하지 않고 `/inquiry/list`의 미확인 답변을 기준으로 확인한다.
- `DELETE_PENDING` 회원은 푸시 구독이 비활성화되므로 제한 화면에서 직접 답변을 확인하도록 한다.
- 답변 알림 저장과 푸시 발송은 후속 개발에서 기존 알림 및 푸시 정책을 따른다.

## 계정 상태별 접근 정책

| 회원 상태 | 문의 등록 | 문의와 답변 조회 | 일반 서비스 | 상태 |
| --- | --- | --- | --- | --- |
| `ACTIVE` | 허용 | 허용 | 허용 | 확정 |
| `SUSPENDED` | 허용 | 허용 | 차단 | 확정 |
| `WITHDRAWN` | 차단 | 차단 | 차단 | 1차 확정 |
| `DELETE_PENDING` | 차단 | 차단 | 차단 | 1차 확정 |
| 회원 물리 삭제 | 불가 | 불가 | 불가 | 확정 원칙 |

`WITHDRAWN` 회원은 같은 Kakao 계정으로 재로그인하여 기존 `USER_NUMB`가 `ACTIVE`로 복귀한 뒤 유지된 문의를 다시 조회한다. 복귀 시 기존 알림과 푸시 구독은 자동 복원하지 않는다.

## 오정지와 탈퇴 상태 처리

### 정지 회원 원본이 존재하는 경우

관리자가 오정지를 확인하고 제재를 해제하면 회원 상태가 여전히 `SUSPENDED`인 경우에만 정책상 복구 상태로 변경한다. 사용자는 최신 인증 상태 확인이 끝난 뒤 일반 서비스로 이동한다.

### 회원이 `DELETE_PENDING`인 경우

제재 해제는 `TH_USSPND`에 반영하되 회원 상태 `DELETE_PENDING`을 덮어쓰지 않는다. 영구탈퇴 취소는 사용자가 별도로 실행하며 유효한 제재가 없으면 `ACTIVE`로 복구한다.

### 회원이 물리 삭제된 경우

- `TM_USERXM`을 복구하지 않는다.
- `TH_USSPND`의 활성 제재만 `RELEASED`로 변경할 수 있다.
- 삭제된 사용자는 기존 문의 답변을 조회할 수 없다.
- 제재 해제 후 같은 Kakao 계정은 새 `USER_NUMB`로 가입할 수 있다.
- 새 계정에 과거 문의와 답변을 연결하지 않는다.

## 재가입 차단과 문의의 역할 분리

고객문의는 동일 Kakao 계정의 재가입을 차단하는 기준 데이터가 아니다. 재가입 판단은 보존된 탈퇴 식별값과 이용정지 이력을 사용한다.

```text
동일 Kakao 식별값 확인
        -> TH_USWTHD에서 기존 USER_NUMB 확인
        -> TH_USSPND에서 ACTIVE 제재 확인
        -> 활성 제재가 있으면 가입 차단
```

`CT_INQURY.SPND_NUMB`는 관리자가 문의와 특정 제재를 함께 검토하기 위한 연결값이다. 관리자가 해당 제재를 `RELEASED`로 변경하면 재가입 판단에서는 활성 제재가 없는 것으로 처리할 수 있다.

## 데이터 보안

- OAuth Kakao 식별값을 `CT_INQURY`와 `CT_INQANS`에 저장하지 않는다.
- 문의 등록과 조회의 회원번호는 인증 정보에서 결정한다.
- 문의 번호만으로 조회하지 않고 작성자 소유권을 함께 검증한다.
- 답변 확인도 답변이 속한 문의의 작성자 소유권을 검증한다.
- `SPND_NUMB`는 로그인 회원의 이용정지 이력인지 서버에서 검증한다.
- 관리자 답변 DTO에 내부 정지 메모와 해제 메모를 포함하지 않는다.
- 문의 내용과 답변을 로그에 원문으로 기록하지 않는다.
- 상태 변경 요청은 기존 CSRF 보호를 적용한다.
- 동시에 여러 관리자가 답변하거나 해제하지 않도록 문의와 제재의 최신 상태를 잠금 조회한다.

## 예외 및 실패 처리

| 상황 | 처리 기준 |

| 답변 등록 전에 다른 관리자가 답변함 | 잠금 조회 후 추가 답변 여부를 확인하고 중복 최종 답변을 차단 |

| 다른 사용자의 문의 번호로 조회 | 존재 여부를 노출하지 않는 공통 실패 응답 |

## 구현 순서

1. 미확정 계정 수명주기와 문의 보존정책을 확정한다.
2. 고객문의 정책 문서를 `docs/policies`에 추가하고 `withdrawal-policy.md`를 동기화한다.
3. `CT_INQURY`, `CT_INQANS`, PK, FK와 인덱스를 `scripts/db/mysql/01-create.sql`에 반영한다.
4. 공통코드와 메뉴 초기 데이터를 `scripts/db/mysql/output/02-admin-insert.sql`에 반영한다.
5. 사용자 고객문의 API와 소유권 검증을 구현한다.
6. 정지 회원의 화면과 API 허용 범위를 수정한다.
7. 사용자 고객문의 화면과 햄버거 메뉴 경로를 연결한다.
8. 관리자 고객문의 API, 권한과 화면을 구현한다.
9. 기존 이용정지 해제 서비스를 고객문의 상세에 연결한다.
10. 사용자, 관리자, 계정 상태 및 동시성 테스트를 수행한다.
11. Sadari 테이블 명세와 관련 정책 문서를 실제 구현에 맞게 동기화한다.

## 완료 조건

- 사용자 햄버거 메뉴에서 `/inquiry/list`로 이동한다.
- 관리자 `사용자 관리 > 고객문의 관리`에서 `/sadari/adm/inquiry`로 이동한다.
- 활성 회원과 정지 회원이 본인 문의를 등록하고 답변을 확인할 수 있다.
- 정지 회원은 고객문의 이외의 일반 서비스에 접근할 수 없다.
- 다른 사용자의 문의와 답변을 조회할 수 없다.
- 관리자가 권한에 따라 문의를 검토하고 답변할 수 있다.
- 이용정지 이의 문의가 정확한 정지 이력과 연결된다.
- 답변만으로 제재가 자동 해제되지 않는다.
- 제재 해제는 별도 권한, 확인과 감사 이력을 남긴다.
- `DELETE_PENDING`을 제재 해제가 덮어쓰지 않는다.
- 물리 삭제 뒤 작성자 연결이 제거되고 새 계정에 과거 문의가 노출되지 않는다.
- 새 계정에 탈퇴 전 문의 내역이 노출되지 않는다.

## 2차 회원 탈퇴정책 개발 항목

2차 개발은 고객문의 기능을 확장하지 않고 정지 회원의 영구탈퇴와 탈퇴 후 제재 유지 및 해제에 필요한 계정 수명주기만 대상으로 한다. 다음 항목은 구현 전에 상세 데이터 구조와 상태 전이를 확정해야 한다.

| 항목 | 제안 | 영향 |
| --- | --- | --- |
| 정지 회원 영구탈퇴 | 30일 유예 영구탈퇴 허용 | 현행 정지 우선 정책 변경 |
| 탈퇴 뒤 Kakao 제재 유지 | `TH_USWTHD.USER_IDHS`와 `USER_NUMB`를 `TH_USSPND`에 연결 | 해시 조회 인덱스와 재가입 판정 설계 |
| 관리자 제재 해제 | 물리 삭제 회원 복구 없이 식별값 단위 해제 | 새 계정 가입 허용 처리 |
| 제재 해제 뒤 재가입 | 같은 Kakao 계정에 새 `USER_NUMB` 발급 | 탈퇴 전 계정과 데이터 미연결 |

위 항목은 1차 고객문의 범위에 포함하지 않으며 2차 회원 탈퇴정책 설계에서 확정한다.
