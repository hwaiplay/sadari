# 사용자 차단 기능 설계

## 개요

- 목적: 사용자가 원하지 않는 상대와 개인 영역에서 서로 발견되거나 상호작용하는 경로를 일관되게 차단한다.
- 적용 범위: 공개 프로필, 공개 독후감, 팔로잉 피드, 팔로우·팔로워 목록, 좋아요 사용자 목록, 댓글·답글, 소셜 알림과 설정의 차단 사용자 관리이다.
- 기준일: 2026년 8월 31일이다.
- 상태: 확정 정책을 반영한 구현 전 설계이며 데이터베이스와 소스에는 아직 적용하지 않았다.
- 정책 기준: [소셜 정책](../policies/social-policy.md)과 [계정 비활성화 및 영구 탈퇴 정책](../policies/withdrawal-policy.md)을 따른다.

## 결론

차단 관계는 방향이 있는 현재 상태 데이터로 저장하되, 노출과 상호작용 판정은 어느 한쪽이라도 상대를 차단했으면 성립하는 양방향 격리로 처리한다. 차단 시 두 사용자 사이의 팔로우 관계는 양방향 모두 삭제하고 차단 해제 후 자동 복원하지 않는다.

차단 시 기존 좋아요와 댓글은 삭제하지 않고 양방향 격리가 유지되는 동안 조회와 집계에서 제외한다. 양쪽의 차단 방향이 모두 해제되면 보존된 반응은 다시 표시하며, 팔로우와 신규 알림만 자동 복원하거나 생성하지 않는다.

공개 소셜 영역에서는 서로의 프로필·콘텐츠·반응을 조회하거나 새 반응을 만들 수 없다. 같은 독서 모임에서는 모임 운영에 필수적인 회원 표시와 공동 콘텐츠를 예외적으로 유지하지만, 상대 프로필 이동과 상대를 대상으로 하는 팔로우·좋아요·댓글·답글 같은 개인 상호작용은 허용하지 않는다.

현재 차단 기능은 미구현이므로 정상 이용 중인 사용자의 현재 프로필 사진과 배경사진은 팔로우 여부와 관계없이 공개 프로필에서 조회하고 반응할 수 있다. 차단 기능을 구현하는 시점에는 이 공개 범위보다 양방향 차단 판정을 우선 적용하고, 이미지 직접 경로와 기존 사진 알림이 공개 프로필 또는 마이페이지로 이동할 때도 현재 차단 관계를 다시 검증해야 한다.

차단 관계는 계정 비활성화와 영구 탈퇴 대기 동안 보존하고 계정이 복귀해도 그대로 적용한다. 회원 원본이 물리 삭제되면 해당 회원이 차단한 관계와 해당 회원을 차단한 관계를 모두 물리 삭제한다.

## 확정 요구사항

### 개인 영역

- 사용자 A가 사용자 B를 차단하면 A와 B 모두 상대의 공개 프로필에 접근할 수 없다.
- 공개 독후감 목록, 팔로잉 피드, 팔로우·팔로워 목록과 좋아요 사용자 목록에서 서로를 제외한다.
- 일반 공개 콘텐츠의 댓글·답글에서는 상대가 작성한 항목을 제외한다.
- 어느 한쪽도 상대를 새로 팔로우하거나 상대 콘텐츠에 좋아요·댓글·답글을 등록할 수 없다.
- 차단 사실과 차단한 사용자의 신원은 상대에게 알림이나 별도 상태로 제공하지 않는다.
- 접근 거절 응답은 존재하지 않는 대상과 구분하기 어려운 공통 안내를 사용한다.

### 기존 관계와 데이터

- 차단 트랜잭션에서 두 사용자 사이의 팔로우 관계를 양방향 모두 삭제한다.
- 차단 해제는 로그인 사용자가 생성한 차단 방향만 삭제한다.
- 상대가 반대 방향의 차단을 유지하면 한쪽이 차단을 해제해도 양방향 격리는 계속 적용한다.
- 차단 자체로 기존 독후감, 댓글, 좋아요와 알림 이력을 삭제하지 않는다.
- 보존된 댓글과 좋아요는 차단 기간에 공개 소셜 조회와 집계에서 제외하고, 양방향 차단이 모두 해제되면 다시 조회 범위에 포함한다.
- 팔로우는 차단 시 삭제하므로 다시 생성하지 않지만, 삭제하지 않고 보존한 좋아요와 댓글의 재표시는 복원 생성으로 보지 않는다.
- 기존 알림은 보존하지만 알림 링크가 차단 대상의 개인 영역이면 서버가 접근을 거절한다.
- 차단 이후 두 사용자 사이에서 발생할 수 있는 신규 개인 소셜 알림과 푸시는 생성하지 않는다.

### 독서 모임 예외

- 차단 전에 이미 같은 모임에 있는 두 사용자는 차단만으로 자동 퇴장시키지 않는다.
- 차단 당사자와 모두 다른 제3자인 모임장이 두 사용자를 각각 초대하는 경우에는 초대와 수락을 허용한다.
- 차단 당사자 중 한 명이 모임장인 모임에서는 두 사용자 사이의 신규 초대, 즉시 가입, 가입 신청과 승인을 허용하지 않는다.
- 차단 전에 차단 당사자 사이에서 직접 발송된 미수락 초대는 차단 트랜잭션에서 만료 처리하고 수락할 수 없게 한다. 제3자인 모임장이 발송한 유효 초대는 유지한다.
- 차단 당사자 중 한 명이 모임장인 모임에 상대가 제출한 처리 중 가입 신청은 차단 트랜잭션에서 취소하고 신청 답변을 삭제하며 처리 알림을 생성하지 않는다.
- 모임 회원 목록, 모임장·운영자 표시, 선정 도서, 투표, 회차와 모임 전용 독후감처럼 공동 운영에 필요한 정보는 표시한다.
- 공동 콘텐츠 안에서는 작성자 닉네임과 운영상 필요한 본문을 표시할 수 있지만 차단 상대의 프로필·배경사진은 기본 이미지로 대체하고 공개 프로필로 이동할 수 없다.
- 차단한 상대의 모임 전용 독후감과 댓글은 운영 문맥을 위해 읽을 수 있으나, 상대를 대상으로 하는 좋아요·댓글·답글 등록은 거절한다.
- 서버는 클라이언트의 모임 여부 값을 신뢰하지 않고 대상 콘텐츠의 모임·회차 연결과 요청자의 활성 모임원 자격을 원본에서 확인한다.
- 모임장과 운영자의 퇴장·제재·승계 권한은 개인 차단의 영향을 받지 않는다.
- 차단 사실과 방향을 별도 상태나 알림으로 제공하지 않는다. 다만 특정 상호작용 제한으로 상대가 차단 관계를 추정할 가능성까지 보장하지는 않는다.
- 향후 모임 채팅을 출시할 때는 시스템 메시지·모임장 공지와 일반 대화의 표시 범위를 별도 정책으로 확정한다.

## 제외 범위

- 관리자 신고 심사, 회원 이용 정지와 모임 강제 퇴장은 개인 차단과 별도 도메인으로 유지한다.
- 차단 이력 분석, 차단 사유 수집과 관리자용 차단 관계 조회는 이번 범위에 포함하지 않는다.
- 모임 채팅은 현재 구현 범위가 아니므로 이번 차단 기능에서 처리하지 않는다.
- 다른 Kakao 계정이나 새로 가입한 계정을 기존 차단 대상과 자동 연결하지 않는다.

## 현행 구조

### 화면

- 공통 사용자 액션 메뉴는 프로필, 공개 독후감 목록과 댓글에서 신고 및 차단 메뉴를 제공한다.
- 차단 확인창과 설정에서 해제할 수 있다는 안내 문구까지 존재하지만 확인 후 실행할 서버 API는 연결되지 않았다.
- 신고 완료 화면에서도 차단 확인창을 다시 열 수 있으나 실제 차단 저장은 수행하지 않는다.
- 설정 화면은 서버에서 관리하는 메뉴 구조를 표시하며 차단 사용자 관리 라우트는 아직 없다.

### 서버와 데이터

- 팔로우와 좋아요는 소셜 기능 영역에서 처리하고, 댓글·피드·알림은 각각 별도 기능 영역에서 처리한다.
- 공개 프로필과 소셜 목록은 활성 계정 및 공개 범위를 검증하지만 사용자 간 차단 관계는 검사하지 않는다.
- 현재 프로필·배경사진 직접 경로는 인증 없이 활성 회원의 현재 사진 여부만 확인하므로 알려진 경로로 차단을 우회할 수 있다.
- 공개 프로필 통계 조회는 조회자 식별값을 받지 않으므로 차단 상대가 제3자를 팔로우하거나 좋아요한 건이 목록에서는 숨겨져도 표시 건수에는 남을 수 있다.
- 모임 전용 비공개 독후감 조회는 활성 모임원 자격을 인정하지만 좋아요·댓글 등록은 일반 공개 콘텐츠 권한을 재사용하므로 모임 문맥과 차단 대상을 함께 판정하는 계약이 필요하다.
- 알림 발송 이력에는 수신자와 완성된 표시 내용이 저장되며 차단 상대를 식별하는 별도 발신자 항목은 없다.
- 영구 삭제 절차는 팔로우, 좋아요, 댓글과 알림을 정리하지만 사용자 차단 관계는 아직 존재하지 않는다.

## 논리 데이터 설계

### 사용자 차단 관계

차단 관계는 현재 유효한 방향성 관계만 저장하는 파생 데이터이다. 차단 사유와 해제 이력을 저장하지 않아 불필요한 민감 관계 데이터 보존을 피한다.

| 논리 항목 | 자료형 | Null | 역할 |
| --- | --- | --- | --- |
| 차단한 사용자 식별번호 | 64비트 정수 | 불가 | 차단을 설정하고 해제할 수 있는 소유자 |
| 차단 대상 사용자 식별번호 | 64비트 정수 | 불가 | 개인 영역에서 격리할 상대 |
| 등록 일시 | 마이크로초 지원 일시 | 불가 | 차단 사용자 목록의 최신 차단순 정렬 기준 |

### 키와 무결성

- 차단한 사용자와 차단 대상 사용자의 조합을 기본키로 사용하여 같은 방향의 중복 차단을 방지한다.
- 두 식별번호가 같은 자기 차단은 서버에서 먼저 거절하고 데이터베이스 검사 제약으로 다시 방어한다.
- 두 사용자 식별번호는 사용자 원본을 참조한다.
- 차단 대상 사용자, 차단한 사용자 순서의 역방향 조회 인덱스를 추가한다.
- 기본키는 사용자가 차단한 목록과 정방향 존재 검사를, 역방향 인덱스는 사용자를 차단한 관계 및 양방향 존재 검사를 지원한다.
- 등록 일시와 대상 식별번호를 함께 사용하는 사용자별 최신 목록 조회 인덱스는 실제 실행 계획에서 기본키만으로 정렬 비용이 큰 경우에 추가한다.

### 저장과 삭제 정책

- 차단 등록은 중복 요청에도 현재 상태를 유지하는 멱등 처리로 구현한다.
- 차단 해제는 로그인 사용자가 소유한 한 방향의 관계만 물리 삭제한다.
- 계정 비활성화와 영구 탈퇴 대기 전환에서는 행을 유지한다.
- 회원 원본 물리 삭제 트랜잭션에서는 해당 회원이 양쪽 식별번호 중 어디에 있든 관련 행을 먼저 삭제한다.
- 별도 차단 이력과 복구용 사본은 저장하지 않는다.
- 신규 기능이므로 초기 데이터 이관은 없으며 빈 관계 데이터에서 시작한다.

## 차단 판정 모델

두 사용자 사이의 격리 여부는 다음 조건으로 판정한다.

```text
격리됨 = 로그인 사용자가 상대를 차단함
      또는 상대가 로그인 사용자를 차단함
```

- 단건 API는 공통 차단 서비스에서 양방향 관계 존재 여부를 검사한다.
- 목록과 집계는 각 행마다 서비스를 호출하지 않고 원본 SQL에서 양방향 차단 관계를 제외한다.
- 같은 응답의 목록, 건수와 페이지 존재 여부에 동일한 차단 조건을 적용한다.
- 화면에서 받은 차단 여부나 사용자 상태를 신뢰하지 않고 인증 사용자 번호로 서버가 다시 판정한다.
- 독서 모임 예외는 공통 판정을 비활성화하지 않는다. 모임 공동 콘텐츠 읽기와 비차단 모임원 대상 반응은 서버가 확인한 모임·회차·회원 문맥에서만 허용하고, 차단 상대를 대상으로 한 상태 변경은 거절한다.

## 기능별 처리 기준

| 기능 | 조회 | 상태 변경 | 비고 |
| --- | --- | --- | --- |
| 공개 프로필 | 양방향 차단 시 공통 접근 거절 | 팔로우 불가 | 차단 방향과 주체를 노출하지 않음 |
| 공개 독후감 | 작성자와 조회자 사이가 차단이면 제외 | 좋아요·댓글 불가 | 상세 직접 접근도 같은 기준 적용 |
| 팔로잉 피드 | 차단 관계 작성자의 모든 카드 제외 | 카드 반응 불가 | 페이지 수 계산 전 원본에서 제외 |
| 팔로우·팔로워 목록 | 로그인 사용자와 차단 관계인 행 제외 | 팔로우 불가 | 조회자별 표시 건수와 목록 범위를 일치시킴 |
| 좋아요 사용자 목록 | 차단 관계 사용자의 좋아요 제외 | 좋아요 불가 | 표시 수와 사용자 목록 범위를 일치시킴 |
| 일반 댓글·답글 | 차단 상대 작성 항목 제외 | 상대 댓글 좋아요·답글 불가 | 부모가 제외되면 연결 답글 묶음도 제외 |
| 알림 | 기존 이력 유지 | 신규 개인 알림 생성 중지 | 링크 진입 시 대상 API가 접근 거절 |
| 차단 사용자 설정 | 내가 차단한 사용자만 닉네임과 기본 이미지로 조회 | 내 방향만 해제 | 나를 차단한 사용자 목록은 제공하지 않음 |
| 독서 모임 | 기존 공동 운영과 제3자 초대 범위 표시 | 상대 대상 개인 반응과 당사자 간 신규 참여 불가 | 관리자 권한은 유지하고 차단 상대 이미지는 기본값 사용 |

### 댓글 스레드

- 일반 공개 영역에서 부모 댓글 작성자가 차단 관계이면 부모와 연결된 전체 답글 묶음을 제외한다.
- 부모는 보이지만 특정 답글 작성자만 차단 관계이면 해당 답글만 제외한다.
- 화면의 댓글 수는 같은 필터를 적용하여 실제 표시 가능한 댓글과 일치시킨다.
- 삭제 댓글 표시 정책은 차단 필터를 통과한 댓글에만 적용한다.
- 독서 모임 공동 콘텐츠에서는 운영 문맥을 위해 댓글 본문을 표시할 수 있지만 차단 상대의 프로필 링크와 직접 답글·좋아요 명령은 제공하지 않는다.

### 좋아요

- 기존 좋아요 행은 차단 시 삭제하지 않는다.
- 로그인 사용자가 보는 좋아요 수와 사용자 목록에서는 차단 상대의 좋아요를 제외한다.
- 양방향 차단이 모두 해제되면 보존된 좋아요 행을 다시 조회와 집계에 포함하며 새 좋아요 행이나 알림은 생성하지 않는다.
- 자신의 좋아요 상태는 차단 상대 콘텐츠 자체가 조회되지 않으므로 일반 공개 영역에서 응답하지 않는다.
- 독서 모임 예외로 콘텐츠가 보이더라도 차단 상대가 소유한 콘텐츠와 댓글에는 좋아요를 등록하거나 취소할 수 없다.

### 알림과 푸시

- 팔로우, 좋아요, 댓글과 답글 등록이 차단 검증에서 거절되므로 해당 개인 알림도 생성되지 않는다.
- 알림 서비스에는 발신 사용자 식별번호를 저장 요청의 선택 내부값으로 전달하고, 수신자와 양방향 차단 관계이면 알림 이력과 푸시를 모두 생략한다.
- 발신자 정보가 없는 시스템 알림과 모임 운영 알림은 차단 대상으로 처리하지 않는다.
- 기존 알림 이력에는 차단 상태를 소급 반영하지 않는다. 링크를 선택하면 연결 API가 현재 차단 관계를 다시 검증한다.
- 차단 여부 때문에 알림 저장을 생략한 사실은 사용자에게 노출하지 않는다.

## API 설계

모든 API는 인증 사용자 번호를 서버 인증 정보에서 사용하고 공통 응답 구조를 반환한다.

| Method | 경로 | 목적 | 주요 응답 |
| --- | --- | --- | --- |
| `POST` | `/api/social/blocks/{userNumb}` | 다른 사용자를 차단하고 양방향 팔로우 관계 삭제 | 차단 완료 여부 |
| `DELETE` | `/api/social/blocks/{userNumb}` | 로그인 사용자가 만든 차단 방향 해제 | 차단 해제 완료 여부 |
| `GET` | `/api/social/blocks` | 로그인 사용자가 차단한 사용자 목록 페이지 조회 | 사용자 요약, 등록 일시, 다음 페이지 여부 |

### 등록 검증

1. 인증 사용자와 대상 사용자 번호의 유효성을 확인한다.
2. 자기 자신인지 확인한다.
3. 대상 회원 원본이 존재하는지 확인하되 실패 응답으로 대상 상태를 자세히 노출하지 않는다.
4. 차단 관계를 멱등 등록한다.
5. 같은 트랜잭션에서 두 사용자 사이의 팔로우 관계를 양방향 삭제한다.
6. 성공한 현재 상태를 반환한다.

대상 회원이 차단 요청 직전에 영구 삭제되면 사용자 참조 또는 존재 검증으로 등록을 중단하고 공통 접근 불가 응답을 반환한다. 차단 등록과 회원 영구 삭제가 동시에 실행되어 고아 관계가 남지 않도록 사용자 원본 참조와 삭제 순서를 유지한다.

### 해제 검증

- 로그인 사용자가 만든 관계만 삭제한다.
- 이미 해제된 요청은 멱등 성공으로 처리하여 재시도 결과를 안정적으로 유지한다.
- 반대 방향 차단 존재 여부는 응답하지 않는다.
- 해제 뒤 삭제된 팔로우를 자동 복원하거나 알림을 새로 만들지 않는다.
- 삭제하지 않고 보존한 좋아요와 댓글은 양방향 차단이 모두 해제되면 다시 조회 범위에 포함한다.

### 목록 조회

- 로그인 사용자가 직접 차단한 방향만 최신 차단순으로 제공한다.
- 활성 대상은 차단 관리에 필요한 현재 닉네임과 기본 이미지만 표시하며 현재 프로필·배경사진과 공개 프로필 상세 이동은 제공하지 않는다.
- 비활성화 또는 영구 탈퇴 대기 대상은 기본 이미지와 접근 제한 상태명만 표시하고 해제 기능은 유지한다.
- 물리 삭제된 대상은 영구 삭제 트랜잭션에서 관계도 제거되므로 목록에 남지 않는다.
- 한 페이지는 프로젝트의 소셜 목록 기준과 동일한 건수를 사용하고 다음 페이지 확인용 한 건만 추가 조회한다.

## 화면 기획

### 차단 진입점

- 다른 사용자 공개 프로필의 더보기 메뉴
- 공개 독후감과 피드 카드의 작성자 더보기 메뉴
- 댓글·답글 작성자의 더보기 메뉴
- 신고 완료 화면의 후속 차단 선택
- 신고 가능한 콘텐츠의 `신고 후 차단하기` 선택

본인 콘텐츠와 본인 프로필에는 차단 메뉴를 표시하지 않는다.

`신고 후 차단하기`는 서버가 신고 원본과 증거를 먼저 저장한 뒤 차단을 실행한다. 신고가 실패하면 차단을 실행하지 않고, 신고는 성공했지만 차단이 실패하면 접수된 신고는 유지한 채 차단 재시도를 제공한다.

### 차단 확인

- 현재 공통 확인창을 재사용한다.
- 양방향 팔로우가 모두 삭제되고 자동 복원되지 않는다는 안내를 추가한다.
- 같은 독서 모임에서는 운영 콘텐츠가 계속 표시될 수 있다는 안내를 추가한다.
- 차단 해제 시 보존된 과거 좋아요와 댓글이 다시 표시될 수 있다는 안내를 추가한다.
- 확인 이후 공통 상태 변경 처리 중 화면으로 중복 제출과 화면 이탈을 막는다.
- 성공하면 같은 모달에서 완료 상태를 표시한 뒤 현재 콘텐츠와 관련 서버 캐시를 제거한다.

### 성공 후 화면

- 공개 프로필에서 차단하면 성공 확인 후 이전 화면으로 이동한다.
- 독후감 상세에서 작성자를 차단하면 성공 확인 후 이전 화면으로 이동한다.
- 목록 또는 피드에서 차단하면 해당 사용자의 모든 카드를 즉시 제거하고 첫 페이지를 다시 조회한다.
- 댓글에서 차단하면 해당 댓글 스레드와 집계를 서버 기준으로 다시 조회한다.
- 신고 완료 화면에서 차단하면 완료 화면을 유지하되 차단 명령을 비활성화한다.
- `신고 후 차단하기`가 성공하면 신고 완료 화면을 유지하고 차단 완료 상태를 함께 표시한다.

### 차단 사용자 관리

- 설정 하위에 `차단한 사용자` 메뉴와 `/settings/blocked-users` 화면을 추가한다.
- 페이지 설명, 차단 사용자 목록, 빈 상태와 페이지 추가 조회를 제공한다.
- 각 행에는 기본 이미지, 닉네임 또는 접근 제한 상태와 `차단 해제` 명령만 표시한다.
- 행 전체를 눌러 상대 프로필로 이동하지 않는다.
- 해제 전 확인창에서 상대가 나를 차단한 경우에는 계속 서로 보이지 않을 수 있음을 직접 언급하지 않는다. 반대 방향 차단 존재를 노출하지 않기 위해 일반적인 해제 안내만 표시한다.
- 해제 성공 후 목록과 소셜 관련 캐시를 다시 조회한다.

## 서버 설계

### 기능 경계

- 소셜 기능 영역에 차단 Controller, Service, Mapper와 요청·응답 DTO를 추가한다.
- 공통 차단 Service는 두 사용자 사이의 양방향 격리 여부와 로그인 사용자의 정방향 차단 여부를 구분해 제공한다.
- 공개 프로필, 독후감, 피드, 댓글, 좋아요, 팔로우와 알림 기능은 공통 판정 계약을 사용한다.
- 프로필·배경사진 직접 조회는 인증 사용자와 사진 소유자의 차단 관계를 검사하고, 차단 상대에게 일반 경로의 이미지 바이트를 제공하지 않는다.
- 공개 프로필의 팔로우·팔로워·받은 좋아요 수는 조회자 식별값을 포함해 목록과 같은 차단 범위로 계산한다.
- 독서 모임 반응 권한은 대상 콘텐츠의 모임·회차 연결과 요청자의 활성 모임원 자격을 서버 원본에서 확인한 뒤 차단 상대 소유 여부를 판정한다.
- 목록 SQL은 공통 Service를 반복 호출하지 않고 동일한 양방향 제외 조건을 각 데이터 조회에 포함한다.

### 트랜잭션

- 차단 관계 등록, 양방향 팔로우 삭제, 당사자 간 미수락 직접 초대 만료와 당사자 소유 모임의 처리 중 가입 신청 취소를 하나의 쓰기 트랜잭션으로 처리한다.
- 어느 단계든 실패하면 차단 관계, 팔로우와 모임 접촉 관계 변경을 모두 롤백한다.
- 차단 해제는 한 방향 관계 삭제만 수행하는 독립 트랜잭션이다.
- 회원 영구 삭제는 차단 관계를 먼저 제거하고 사용자 원본을 마지막에 삭제한다.
- 차단 등록 후 캐시 갱신 실패는 데이터베이스 상태를 되돌리지 않고 클라이언트가 최신 목록을 재조회하도록 처리한다.

### 권한과 정보 노출

- 클라이언트가 전달한 차단 사용자 번호나 차단 방향을 신뢰하지 않는다.
- 나를 차단한 사용자 목록과 반대 방향 차단 여부를 API로 제공하지 않는다.
- 차단 때문에 거절된 프로필·콘텐츠·가입 API는 `누가 누구를 차단함`을 메시지에 포함하지 않는다. 공유 모임의 제한된 동작으로 관계를 추정할 가능성은 잔여 위험으로 안내한다.
- 관리자 API에 개인 차단 관계를 기본 제공하지 않는다.
- 운영 로그에는 두 사용자 번호와 처리 결과만 최소한으로 남기며 닉네임·프로필·콘텐츠 원문을 기록하지 않는다.

## 조회 영향 범위

### 반드시 변경할 조회

- 공개 프로필, 공개 독서 요약과 공개 독서 통계
- 공개 프로필의 조회자별 팔로우·팔로워·받은 좋아요 수
- 현재 프로필·배경사진의 직접 이미지 조회
- 공개 독후감 목록과 독후감 상세 접근 검증
- 팔로잉 피드 카드, 좋아요 수와 댓글 수
- 팔로우·팔로워 목록과 팔로우 상태
- 좋아요 수, 좋아요 사용자 목록과 좋아요 대상 접근 검증
- 일반 댓글·답글 목록, 댓글 수와 댓글 좋아요 수
- 신고 화면이 접근하는 현재 원본 조회
- 모임 전용 독후감·댓글의 조회와 좋아요·댓글·답글 상태 변경 권한

신고 이력과 관리자 전용 스냅샷은 차단과 무관하게 유지한다. 일반 사용자가 차단 상대의 숨겨진 콘텐츠를 새 신고 대상으로 조회할 수는 없으므로, 콘텐츠를 확인한 시점의 `신고 후 차단하기`는 신고 원본 저장을 먼저 완료해야 한다.

### 명시적 예외 조회

- 본인 마이페이지의 본인 데이터
- 설정의 차단 사용자 관리 목록
- 독서 모임 회원·운영·회차·투표와 공동 콘텐츠 조회. 차단 상대의 사진은 기본 이미지로 대체한다.
- 관리자 신고·회원 관리와 감사 이력
- 시스템 알림과 모임 운영 알림 생성

## 캐시와 화면 상태

- 차단 성공 후 공개 프로필, 팔로우 상태·목록, 피드, 공개 독후감, 댓글과 좋아요 사용자 목록 캐시를 무효화한다.
- 차단 대상 사용자의 카드만 클라이언트에서 제거한 상태를 최종 결과로 간주하지 않고 서버 첫 페이지를 다시 조회한다.
- 차단과 해제 중 같은 대상에 대한 중복 요청을 막는다.
- 다른 탭에서 차단 상태가 바뀐 뒤 상세 요청이 실패하면 공통 접근 불가 안내 후 안전한 이전 화면으로 이동한다.
- 로그아웃 시 차단 목록을 포함한 계정별 서버 캐시를 제거한다.

## 동시성과 실패 처리

| 상황 | 처리 |
| --- | --- |
| 같은 대상 차단을 연속 제출 | 기본키와 멱등 등록으로 한 관계만 유지 |
| 양쪽이 동시에 서로 차단 | 방향별 관계를 각각 저장하고 양방향 팔로우 삭제는 멱등 처리 |
| 차단과 팔로우가 동시에 실행 | 상대 관계 잠금 또는 동일한 차단 재검증으로 차단 완료 뒤 팔로우가 남지 않게 처리 |
| 차단과 좋아요·댓글 등록이 동시에 실행 | 쓰기 직전 차단 관계를 다시 검증하고 차단 관계가 확정되면 반응 저장을 거절 |
| 차단 해제와 반대 방향 차단 | 한 방향만 삭제하고 반대 방향이 남으면 격리 유지 |
| 차단 대상 영구 삭제 | 영구 삭제 트랜잭션이 관련 차단 관계를 먼저 제거 |
| 목록 조회 중 차단 상태 변경 | 다음 조회에서 서버 원본 기준으로 반영 |
| 알림 생성 직전 차단 | 알림 저장 직전에 양방향 관계를 확인해 신규 알림과 푸시 생략 |
| 신고 후 차단 중 신고 실패 | 차단을 실행하지 않고 신고 입력 화면에서 재시도 제공 |
| 신고 성공 후 차단 실패 | 신고 이력은 유지하고 완료 화면에서 차단만 재시도 |
| 차단과 미수락 직접 초대 | 차단 당사자 사이의 직접 초대만 만료하고 제3자 초대는 유지 |
| 차단과 처리 중 가입 신청 | 차단 당사자가 모임장인 모임의 상대 신청만 취소하고 답변 삭제와 무알림 처리를 함께 확정 |

차단과 팔로우의 경쟁 조건은 두 사용자 번호를 작은 값부터 일관된 순서로 잠그거나 차단 관계 등록 후 팔로우 삭제와 팔로우 등록 직전 차단 재검증을 조합해 교착과 잔존 관계를 방지한다.

## 성능 설계

- 양방향 관계 확인은 정방향 기본키와 역방향 인덱스를 사용한다.
- 목록에서는 사용자별 상관 서브쿼리를 여러 번 실행하지 않고 차단 관계를 한 번만 결합하거나 두 방향의 존재 검사를 인덱스로 처리한다.
- 집계와 목록에 같은 필터를 적용하되 중복 조인으로 행 수가 증가하지 않게 존재 조건을 우선 사용한다.
- 차단 관계 데이터 규모와 공개 목록 실행 계획을 확인한 뒤 사용자별 최신 목록 전용 인덱스 추가 여부를 결정한다.
- 예상 효과는 비공개 데이터를 애플리케이션으로 가져오지 않고 데이터베이스에서 제외하는 것이며, 실제 응답 시간과 실행 계획은 구현 후 측정한다.

## 구현 순서

1. 소셜 및 계정 수명주기 정책 문서를 확정 상태로 갱신한다.
2. 사용자 차단 관계의 생성 정의와 기존 환경 적용 인덱스 원본을 갱신한다.
3. 테이블 명세의 논리 설명, 키, Null과 인덱스 정보를 승인된 원본과 동기화한다.
4. 차단 등록·해제·목록과 공통 판정 Service를 구현한다.
5. 차단 등록 트랜잭션에 양방향 팔로우 삭제를 연결한다.
6. 공개 프로필·독후감·피드·팔로우·좋아요·댓글 조회와 상태 변경에 양방향 검증을 적용한다.
7. 프로필·배경사진 직접 조회와 공개 프로필 집계에 인증 조회자 기준을 적용한다.
8. 모임 공동 콘텐츠의 서버 원본 문맥 검증과 당사자 간 신규 참여 제한을 적용한다.
9. 신고 원본 저장을 선행하는 `신고 후 차단하기` 흐름을 연결한다.
10. 알림 요청에 내부 발신자 식별값을 전달하고 신규 알림·푸시 억제를 적용한다.
11. 회원 영구 삭제 절차에 양방향 차단 관계 정리를 추가한다.
12. 차단 확인창을 실제 API와 연결하고 설정의 차단 사용자 관리 화면을 추가한다.
13. 설정 사용자 메뉴와 라우트를 연결하고 다국어 메시지를 동기화한다.
14. 서버 통합 테스트, Mapper 테스트와 프론트엔드 상태·접근성 테스트를 실행한다.
15. 실제 실행 계획, 페이지 경계와 모임 예외 회귀를 검증한 뒤 배포한다.

## 테스트 계획

### 데이터와 서비스

- 자기 차단, 존재하지 않는 사용자와 중복 차단을 검증한다.
- 한 방향 차단만 있어도 양쪽 요청에서 격리되는지 검증한다.
- 차단과 양방향 팔로우 삭제가 같은 트랜잭션으로 성공·롤백되는지 검증한다.
- 한 방향 해제와 반대 방향 차단 유지 조합을 검증한다.
- 비활성화·영구 탈퇴 대기·복귀와 영구 삭제의 보존·삭제 범위를 검증한다.
- 동시 차단·팔로우 요청에서 차단 후 팔로우 관계가 남지 않는지 검증한다.

### 조회와 집계

- 공개 프로필·독후감·피드에서 양쪽 사용자가 서로 제외되는지 검증한다.
- 팔로우·팔로워·좋아요 사용자 목록과 표시 건수가 같은 범위인지 검증한다.
- 제3자 프로필의 팔로우·팔로워·받은 좋아요 수가 조회자의 차단 관계를 반영해 목록과 일치하는지 검증한다.
- 차단 상대의 알려진 현재 프로필·배경사진 경로를 직접 요청해도 이미지 바이트가 반환되지 않는지 검증한다.
- 차단된 부모 댓글의 전체 스레드와 차단된 답글만 각각 올바르게 제외되는지 검증한다.
- 페이지 경계에서 차단 필터 때문에 중복·누락·빈 중간 페이지가 발생하지 않는지 검증한다.
- 차단 해제 뒤 보존된 좋아요와 댓글이 다시 조회되고 팔로우는 복원되지 않는지 검증한다.

### 독서 모임

- 기존 공동 모임은 유지되고 제3자인 모임장의 초대와 수락만 허용되는지 검증한다.
- 차단 당사자가 모임장인 모임의 신규 가입·신청·승인·초대와 차단 전 미수락 직접 초대가 거절되는지 검증한다.
- 차단 당사자 소유 모임의 처리 중 가입 신청이 취소되고 답변과 처리 알림이 남지 않는지 검증한다.
- 공동 회원·회차·투표·독후감·댓글이 운영 범위에서 표시되는지 검증한다.
- 차단 상대의 모임 프로필·배경사진은 기본 이미지로 표시되는지 검증한다.
- 차단 상대의 공개 프로필 이동, 팔로우, 좋아요와 직접 댓글·답글이 거절되는지 검증한다.
- 클라이언트가 모임 여부를 위조해도 서버 원본의 모임·회차·활성 모임원 관계 없이 비공개 콘텐츠에 반응할 수 없는지 검증한다.
- 모임장 퇴장·제재·승계가 개인 차단과 무관하게 동작하는지 검증한다.
- 응답과 화면에 차단 방향과 차단 주체가 노출되지 않는지 검증한다.

### 알림과 화면

- 차단 이후 개인 소셜 알림과 푸시가 생성되지 않는지 검증한다.
- 기존 알림은 남지만 차단 대상 링크 접근이 거절되는지 검증한다.
- 프로필·독후감·피드·댓글·신고 완료 화면의 차단 진입점을 검증한다.
- `신고 후 차단하기`가 신고 성공 뒤에만 차단하고 부분 실패 시 확정된 신고를 유지하는지 검증한다.
- 차단 성공 후 관련 목록과 집계가 서버 원본으로 갱신되는지 검증한다.
- 설정의 차단 사용자 목록, 빈 상태, 추가 조회와 해제 확인을 검증한다.
- 모바일·데스크톱, 키보드 포커스, 보조기기 이름과 처리 중 이탈 차단을 검증한다.

## 배포와 롤백

- 관계 저장소와 조회 인덱스를 먼저 배포한 뒤 서버, 사용자 메뉴 기준정보와 프론트엔드를 순서대로 배포한다.
- 서버 배포 전에는 차단 UI가 실제 저장 성공을 안내하지 않도록 프론트 기능을 활성화하지 않는다.
- 배포 검증은 차단 등록·해제, 공개 프로필 거절, 목록 필터, 신규 알림 억제와 모임 예외를 포함한다.
- 롤백 시 프론트 진입점을 먼저 비활성화하고 이전 서버로 복구한다. 관계 데이터는 즉시 삭제하지 않아 재배포 시 사용자의 차단 선택을 보존한다.
- 관계 저장소 제거는 기능 폐기와 데이터 삭제 범위를 별도로 승인한 뒤 수행한다.

## 대안과 선택 이유

### 비방향성 한 행

사용자 번호 두 개를 정렬해 한 행만 저장하면 격리 여부는 단순하지만 누가 차단을 설정했고 누가 해제할 수 있는지 표현할 수 없다. 방향성 관계를 저장하고 조회에서 양방향으로 판정하는 방식을 선택한다.

### 팔로우 관계 보존

팔로우를 숨긴 채 보존하면 차단 해제 순간 관계가 사용자 동의 없이 복원된다. 차단 시 양방향 팔로우를 삭제하고 해제 후 각 사용자가 다시 팔로우하도록 한다.

### 모든 기존 반응 삭제

차단 시 댓글과 좋아요까지 물리 삭제하면 제3자 콘텐츠의 대화와 집계를 복구할 수 없게 변경한다. 기존 반응은 보존하되 로그인 사용자별 조회에서 제외하는 방식을 선택한다.

### 독서 모임 공동 참여 금지

공동 참여를 전면 금지하면 제3자인 모임장의 초대가 실패하고 기존 모임에서는 자동 퇴장 대상을 결정하기 어렵다. 기존 공동 모임과 제3자인 모임장의 초대만 유지하고, 차단 당사자가 모임장인 공간으로의 신규 참여와 직접 초대는 제한하는 예외를 선택한다.

## 남은 위험

- 기존 알림 본문에는 과거 상대 닉네임이 남을 수 있다. 확정 정책은 이력을 보존하므로 링크 접근만 차단한다.
- 독서 모임 공동 콘텐츠에서는 운영상 상대 닉네임과 본문이 보일 수 있어 개인 영역의 완전한 비노출과 다르다. 차단 확인창에서 이 예외를 안내해야 한다.
- 독서 모임에서 특정 프로필 이동과 반응이 제한되면 상대가 차단 관계를 추정할 수 있다. 차단 방향과 주체를 명시적으로 제공하지 않는 것을 보장 범위로 한정한다.
- 브라우저가 차단 전에 받은 이미지를 메모리나 디스크 캐시에 보관할 수 있으므로 서버는 이후 재검증 요청을 차단하되 이미 내려간 바이트의 회수까지 보장하지 않는다.
- 양방향 필터가 여러 Mapper에 반복되므로 누락 가능성이 있다. 공통 검증 목록과 기능별 통합 테스트를 완료 기준으로 사용한다.
- 차단과 팔로우·반응의 동시 요청은 단순 사전 조회만으로 경쟁 조건을 막지 못한다. 구현 시 잠금 순서와 쓰기 직전 재검증을 함께 적용해야 한다.
- 현재 알림 이력 구조만으로 과거 알림을 발신자별로 일괄 숨길 수 없다. 기존 알림 보존 정책을 변경하려면 별도 데이터 계약이 필요하다.

## 완료 기준

- 어느 한쪽의 차단만으로 개인 소셜 영역에서 양쪽이 서로 노출되지 않는다.
- 차단 등록과 양방향 팔로우 삭제가 하나의 트랜잭션으로 처리된다.
- 목록, 집계, 상세 접근과 상태 변경이 동일한 서버 차단 기준을 사용한다.
- 차단 해제는 자신의 방향만 제거하고 팔로우를 자동 복원하지 않으며 양방향 차단이 모두 해제되면 보존된 좋아요와 댓글만 다시 표시한다.
- 프로필·배경사진 직접 조회와 공개 프로필 집계도 인증 조회자의 차단 관계를 적용한다.
- 신규 개인 소셜 알림과 푸시는 중지되며 기존 알림 링크는 현재 접근 정책을 따른다.
- 기존 독서 모임의 공동 운영과 제3자 모임장 초대는 유지하면서 당사자 간 신규 참여와 개인 상호작용은 제한한다.
- 신고 가능한 콘텐츠의 원본을 먼저 저장한 뒤 차단하는 `신고 후 차단하기`가 부분 실패 기준을 지킨다.
- 계정 비활성화·영구 탈퇴 대기·복귀·물리 삭제 정책이 코드와 테스트에 반영된다.
- 설정에서 자신이 차단한 사용자만 확인하고 해제할 수 있다.
- 관련 정책, 데이터 정의, API 문서, 다국어 메시지와 테스트가 구현 결과와 동기화된다.
